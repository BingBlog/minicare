# TECH-018 — 多语言语料知识库的翻译策略调研（英文语料 × 中文场景）

> 文档编号：TECH-018 ｜ 版本：v0.1 ｜ 日期：2026-10-09 ｜ 状态：**调研完成，方案建议待拍板**
> 上游：[`PRD-008`](../prd/PRD-008/README.md)（知识库平台化）｜ 配套技术方案：[`TECH-015`](TECH-015-kb-platform.md)（KB 平台）
> 运维速查：[`TECH-015-kb-platform-gotchas.md`](TECH-015-kb-platform-gotchas.md)
> 触发问题：语料含相当比例英文原文（国际文献）。在「解析确认、检索、LLM 消费」三处，纯英文专业术语对人工核对与中文用户不友好；翻译应该放在管线哪个位置？
> 本文性质：**行业调研 + 初步方案建议**，非实现级设计。落地设计需另行评审后开工。来源分三层：学术论文 / 官方文档 > 厂商生产实践博客 > 社区文章；结论冲突处已标注。

## 0. 结论速览

| # | 结论 |
|---|---|
| **C-1** | **「解析前翻译」是行业反模式** —— 没有 RAG 管线先把整档 PDF 翻译再解析；翻译一律发生在**文本层（解析之后）**，最细到块级。本地化行业的"整档翻译"也是先抽取文本再重排版式，不碰版式解析。 |
| **C-2** | 行业真实存在的插入点有 **4 个**：B 入库时（解析后/切片级）、C 查询期、D 向量层（多语言 embedding，两者都不翻）、E 消费期（LLM 直读原文）。 |
| **C-3** | **没有纯单点方案** —— 生产系统全是组合拳（典型：B+E「入库翻译 + 消费回译」、D+E「多语言向量 + 消费翻译」）。 |
| **C-4** | 检索质量的稳定结论：**文档侧翻译 > 查询侧翻译**（CLIR 数十年实证，2025 年 mRAG 论文仍在复现）；查询翻译胜在便宜即时，输在术语歧义与覆盖。 |
| **C-5** | 行业按语料形态分流：**小而稳定的高价值语料**（专利 / 法规 / 产品手册）→ 离线文档翻译；**巨大且高速变化** → 查询翻译；**多语混杂的私域** → 多语言向量（近年的默认答案）。 |
| **C-6** | 医疗 / 监管场景共识：**原文是唯一权威，翻译只是辅助**；受控术语表优先（MedDRA 式"官方译名必须使用"）；机翻必须配人工复核（ISO 18587 后编辑）且全流程可追溯。 |
| **C-7** | 对本项目建议：**新增块级「双语对」产物（原文为准 + 译文为辅），插在 `validate → translate → index` 之间**；译文同时服务人工核对、检索增强与 LLM 上下文；原文永久保留、引用锚点不变。查询翻译 / 多语言向量列为后续实测选项（§6.4）。 |

## 1. 背景与问题定义

### 1.1 触发场景

语料 20 份（16 PDF + 4 HTML），其中国际文献为英文原文。三个触点上"英文不友好"：

| 触点 | 具体表现 | 影响谁 |
|---|---|---|
| ① 解析确认 | 核对解析结果、数字回填、切块校对时需要读懂英文 | 知识库建设者（人）——当前最费劲的环节 |
| ② 检索 | 中文查询 × 英文文档的跨语言召回，依赖 embedding 的跨语言能力（现模型 `kinfra-text-embedding-0.6b` 为中文向，该能力**未做过专项评估**） | 检索效果 |
| ③ LLM 消费 | agent 读英文块生成回答。LLM（DeepSeek）中英都强，本身问题不大；但"回答中的引用片段"对最终读者（家长）不友好，且**知识库建设者希望对内容有认知**的需求在此延续 | 终端用户 + 建设者 |

> 注意：这是一个"**人**要读懂内容"的需求 × "**检索**要跨语言匹配"的需求 × "**LLM**要消费内容"的需求的叠加，不是单纯的检索效果问题。行业调研也按这个三分法组织。

### 1.2 现状约束（决定方案的硬边界）

- 六步管线：`preflight → parse → normalize → segment → validate → index`；每步独立产物、独立参数哈希、独立缓存失效（TECH-015 §4）。
- **行号链对齐**（切片 ↔ 原文 100% 命中）+ PDF 文字层校验（`find_continuations`）——翻译方案不得破坏这两条链路。
- 人工产物层 `edits/`；前端工作台已有「解析对照」「切片对照」两个双语展示的天然落点。
- 评估基线：45 题精确召回回归（当前 97.8%），是目前唯一可量化的检索口径 —— 任何检索侧改动都应先扩充该口径（§6.3）。
- **硬性推论**：翻译不能放在解析前 —— 否则整条对齐链、文字层校验、版式解析全部失效（与 C-1 的行业结论一致，不是本项目独有约束）。

### 1.3 调研问题

翻译应该放在 **解析前 / 入库时 / 检索时 / 消费时** 哪一环？行业怎么选、为什么、代价是什么？

## 2. 五个翻译插入点（行业全景）

先给全景，再逐点展开。**"是否翻译语料"与"是否翻译查询"是两条独立的轴**，真实系统各选一点组合。

| # | 插入点 | 一句话原理 | 翻语料 | 翻查询 | 行业采用度 | 代表系统 |
|---|---|---|---|---|---|---|
| **A** | 解析前 | 先翻整档文件、再解析 | ✅（翻文件） | — | ❌ 几乎无人做 | 无（反模式，见 §2.1） |
| **B** | 入库时 | 解析后、文本层 / 块级产出译文（双语或单语入库） | ✅ | — | **高** | 专利局、法规翻译、Azure 索引期翻译、企业文档 |
| **C** | 查询期 | 语料不动，把查询翻译成文档语言再检索 | ❌ | ✅ | **高** | 网页搜索（CLIR 传统）、客服机器人、IBM 方案 |
| **D** | 向量层 | 两者都不翻，多语言 embedding 共享向量空间 | ❌ | ❌ | **上升中** | 欧盟私域 RAG 默认、BGE-M3 / mE5 体系 |
| **E** | 消费期 | LLM 直读原文，用目标语言生成（或再后翻） | ❌ | ❌ | **高（兜底层）** | 几乎所有跨语言 RAG 的最终一层 |

### 2.1 A：解析前整档翻译 —— 行业反模式，本项目硬性排除

**调研结论：找不到任何 RAG / 知识库管线把翻译放在 OCR、解析之前。** 理由在行业侧同样成立：

1. **版式解析器不是为译文准备的**：MinerU 等解析引擎依赖原文的版式信号（栏、页眉、字体层级）。翻译发生在"重排后的译文"上会让解析器面对一份"没有原生版式的合成文档"，此前解析原文的收益全部丢失。
2. **对齐与溯源断裂**：检索命中的译文必须能跳回原文位置（本项目的行号链、PDF 文字层校验都建立在"文本 = 原文"的前提上）。翻完再解析，等于重新造一条对齐链。
3. **术语与数字会在最上游被改写**：越早翻译，错误传播越远（校验、切片、索引全部继承翻译误差）。行业经验是**"翻译尽量贴近消费端"**而不是贴近源头。

> 唯一形似"解析前翻译"的是**本地化行业的整档文档翻译**（如 Azure Document Translation、各文档翻译 API）：但它的正确位置是**入库环节**——先由文档感知的抽取器（自带 OCR/版式理解）拿到结构化文本，再逐字段翻译、最后按原文结构重排。也就是说：**"整档"是交付形态，"翻译"仍在文本层发生**。文档翻译 API 的价值点（layout preservation，表格/多列不塌陷）恰恰说明行业认为"结构正确"与"翻译"是两件事，不能混。

### 2.2 B：入库时翻译（translate-then-index）—— 检索质量最稳

**做法**：解析后（通常在归一化 / 切片层）把文本翻译到目标语言，译文（或双语对）入索引；查询语言固定为单一语言，检索退化为**单语检索**。

**行业证据**：
- **CLIR 经典结论**（信息检索教科书层面，2020s 仍被引用）："小而稳定的高价值文集用文档翻译（译一次、服务无数次查询）；巨大且高速变化的文集用查询翻译（每次只翻 5 个词）。专利、法律、产品手册类库一律用离线文档翻译。"
- **云端索引期翻译是标准能力**：Azure AI Search 的两种多语言模式 —— ①语言专属索引 ②混合索引（每字段按语言多版本，如 `description_en`/`description_fr`）+ 索引期挂 Text Translation 技能；并明确"RAG 场景下也可以让 LLM 在 prompt 层返回译文"作为轻量替代。
- **文档侧翻译的检索质量优势**被 mRAG 论文持续复现（见 §3）：文档上下文长，机器翻译有更多语料可利用，歧义更少；查询短，翻译歧义不可控。
- **生产基准**（Hoverbot，14 语言 / 5000 万+ 查询）：在其内部评测集上，"**先翻到基准语言 + 单语 embedding**"的组合，跨语言一致性甚至**超过**直接用多语言 embedding 模型。

**代价**：
- 翻译成本前置（一次性 + 增量）；译文与原文的**双份版本漂移**需要工程兜底（缓存 / 版本化）。
- 翻译错误固化为"检索事实" —— 缓解手段是**受控术语表 + 质量标记**（见 §3 QTT-RAG）。
- 存储翻倍（可接受；本库 1586 条量级下可忽略）。

### 2.3 C：查询期翻译 —— 便宜即时，术语最易失真

**做法**：语料保持原文，检索前把用户查询翻译为文档语言（或 pivot 到英语），检索后生成阶段再回到用户语言。

**行业证据**：
- IBM watsonx 的官方 RAG 架构模式：pre/post-query translation —— 查询翻成语料基准语言 → 检索 → 生成 → 回答翻回用户语言；"经验上非母语场景可达 80%+ 准确度"。
- 网页搜索传统选择查询翻译，原因是索引巨大且秒级更新，翻全库不现实；典型延迟 15–40ms/查询。
- 中文社区共识（CSDN 等）：**这些场景适合**翻译查询 —— 用户主要说中文、文档主要英文、术语稳定、可接受一次 LLM 改写延迟；**这些场景不适合** —— 查询含产品别名/内部黑话、文档本身语言混杂、查询极短（翻译后语义漂移）。

**主要失效模式**（多篇来源一致）：领域术语被翻坏（"quantum tunneling" → "quantum digging"）、缩写丢失（HPA → Horizontal Pod Autoscaler）、短查询歧义、翻译错误静默地导致"引用了错误的文档"而不是"查不到"。缓解手段：术语保护（实体遮挡/占位符）、低置信度时回退到跨语言向量检索、混合检索（稀疏用译文查询 + 稠密用跨语言）。

### 2.4 D：向量层跨语言（多语言 embedding）—— 维护最省

**做法**：语料与查询都不翻译，把两者编码进共享向量空间（BGE-M3、multilingual-e5、mContriever、LaBSE 等）。检索天然跨语言。

**行业证据**：
- 欧盟企业私域 RAG 的"可行默认"（vdf.ai）：三架构并列（翻译后入库 / 多语言向量 / 分语种索引 + 查询路由），**默认推荐多语言向量**——一个索引、一套权限、一个修问题的地方；并强调"答案用用户语言、引用保持原文语言"（答案语言与引用语言分离）。
- 多语言 embedding 的实际质量**因语言组而异**：生产博客实测同一批内容的 EN/JA/ZH 召回差异可达 ~7 个百分点、跨语言一致率 81–88%（取决于模型），且"升级模型可能整体变好、个别语言变差" —— **必须按语言评测，不能只看聚合指标**。
- 对本项目的特殊约束：现役 embedding 为中文向小模型（0.6b，当年实测优于 4b 的多语言版本——"4b 高维多语言能力在 95% 中文小语料上是负收益"）。换多语言模型 = 全库重编码 + 重测 97.8% 基线，属于高风险改动（S-3 选型已被实测锁定）。

### 2.5 E：消费期翻译 —— 最轻兜底，行业普遍存在

**做法**：检索给到英文原文块，LLM 直接阅读并用用户语言生成回答（或生成后加一道翻译）。语料零改动。

**行业证据**：
- 这是几乎所有跨语言 RAG 的**最后一道兜底**，也是"只做这一个"时的最省方案。
- 学术上被证实有两个真实挑战（XRAG，Amazon AGI）：①**回答语言正确性** —— 模型可能不自觉切换语言或中英混杂；②**跨语言推理** —— 多个语言来源混合时，模型整合能力下降。也就是说"LLM 能读英文"不等于"消费期零成本"。
- 对**人工核对**（本项目的触点①）完全无帮助 —— LLM 能读，人还是要读英文。

### 2.6 生产系统全景：全是组合拳

| 组合 | 出处 | 结构 |
|---|---|---|
| **B + E** | Hoverbot（客服域，14 语言） | 入库翻译到单一基准语言 → 单语索引检索 → 生成（带引用）→ 回译 + 实体还原。核心口号："translate at the edges, reason in one base language"。 |
| **D + E** | vdf.ai（欧洲私域） | 多语言向量检索原文 → 用用户语言生成答案 → 引用保留原文。默认路线。 |
| **C + E** | IBM watsonx / 网页搜索 | 查询翻译 → 单语检索 → 生成 → 回译。查询短、索引大的场景。 |
| **B/D + 质检 + E** | 学术前沿（CrossRAG / QTT-RAG，§3） | 检索后把文档翻到查询语言、附翻译质量标签再生成 —— 论文实验里效果最好的一档。 |

## 3. 学术实证（给"文档翻译 vs 查询翻译"一个可引用的判断）

| 来源 | 结论 | 对本项目的含义 |
|---|---|---|
| CLIR 传统（McCarley 1999 → 2025 多篇复现） | **文档翻译 > 查询翻译**（检索质量）；查询翻译赢在成本 | 支持"入库翻译"作为质量上限方案 |
| CrossRAG（arXiv 2504.03616，Edinburgh） | 查询翻译（tRAG）覆盖有限；把**检索到的文档**翻成共同语言再生成（CrossRAG），知识密集任务显著提升，高低资源语言都受益 | "翻检索结果"是比"翻查询"更保险的中间档 |
| QTT-RAG（arXiv 2510.23070，延世大/LG） | 给译文附**三维质量分**（语义等价 / 语法 / 流畅度）作为元数据，让生成器知道"这段翻译多可信"，优于让 LLM 重写译文（重写会引入幻觉） | 若做机翻，**保留质量标记**、不做 LLM 二次改写 |
| XRAG（arXiv 2505.10089，Amazon AGI） | 跨语言 RAG 的两大真实挑战：回答语言正确性、跨语言推理；不是"看不懂" | 消费期方案要显式约束回答语言；混合语言来源要小心 |
| Futurepedia（arXiv 2410.21970，厦大/通义） | 语言不平等：英语在知识选择上存在系统性偏差；低资源→高资源翻译有级联误差风险 | 英文语料占比高时，注意"英文来源系统性压过中文来源" |

## 4. 分行业实践速查

| 行业 / 系统 | 做法 | 关键细节 | 启示 |
|---|---|---|---|
| **医疗 / 药监**（EMA、MedDRA 体系） | 原文权威 + 受控术语 + 人工复核 | MedDRA **官方译名必须原样使用**，无官方译名则保留英文 + 标注；SmPC 与患者说明书两级用词；机翻可以，但必须人审（ISO 17100 / ISO 18587 后编辑），全流程可追溯 | 术语表是医疗翻译的第一优先级；"原文为准"是审计要求不是偏好 |
| **专利**（WIPO Translate / EPO Patent Translate / Espacenet） | **翻译仅用于检索与粗读**，不具法律效力 | 专利局自建专利域 NMT（质量高于通用翻译）；FTO 等关键决策必须另做专业翻译；"machine translation is for triage only" | "译文用于找人、原文用于定事" —— 双轨的典型样板 |
| **企业搜索 / 云厂商**（Azure AI Search / IBM watsonx） | 索引期翻译技能 / 字段级多语言索引 / 查询前后翻译 | Azure：语言分析器 + 混合索引 + Text Translation 技能（索引期）；IBM：pre/post-query translation 模式（80%+ 经验值） | 入库翻译是被云厂商产品化的标准动作，不是自创 |
| **欧盟私域 RAG**（vdf.ai 等） | 多语言向量为默认；分语种索引 + 查询路由为例外 | 强调：**答案用用户语言、引用保持原文语言**；chunking 需按语言适配（Token 数因语言膨胀） | "答中文、引原文"是稳妥的呈现策略 |
| **生产级多语言 RAG**（Hoverbot） | 入库翻译 + 单语索引 + 回译 | 实体保护（SKU/编号/术语先遮挡后还原）；通用术语表；**逐语言评测**；翻译质量 + 实体保护 > embedding 选择 | 若翻译入库：先做术语保护与评测两件事，再谈架构 |
| **中文社区实践**（CSDN / aiknowledge / QAnything） | 分歧明显，按场景分流 | 一曰"全翻成中文通常不是好主意"（成本 / 更新漂移 / 术语噪音三宗罪）；一曰"仅 1–2 门外语且精度要求高（法律医疗）→ 查询翻译更稳；多语混杂 → 多语言向量" | 存在"**反对全量翻译**"的合理声音——因其假设是"LLM 能读原文"，对人机双读者与术语受控场景不成立 |
| **开源 RAG 框架**（LlamaIndex 生态） | 不内置策略 | 官方文档给两条路：多语言 embedding 或接翻译 API；无默认答案 | 没有"标准答案"，每个项目按自身约束自决 |

## 5. 决策因子（怎么给自己选）

| 因子 | 偏向 B 入库翻译 | 偏向 C 查询翻译 | 偏向 D 多语言向量 |
|---|---|---|---|
| 语料规模与更新频率 | **小而稳定**（译一次用多次） | 大、秒级快变 | 任意（模型定上限） |
| 术语精度要求 | 高（可用受控术语表译一次、全库一致） | 低–中（短查询歧义不受控） | 中（取决于模型） |
| 是否要服务**人工核对** | **是（双语产物是唯一直接收益方）** | 否 | 否 |
| 运维预算 | 中（翻译管线 + 术语表 + 版本缓存） | 低 | 中（换模型 + 逐语言评测） |
| 溯源 / 审计 | 强（双语对照可审） | 弱 | 中（保留原文） |
| 延迟敏感度 | 不敏感（离线批处理） | 敏感（每查询 +15–40ms） | 最不敏感 |
| 已知风险 | 翻译错误固化、版本漂移 | 术语翻坏、静默召回错误 | 语言质量波动、偏差 |

**本项目在因子上的位置**：语料小且稳（✅ B）｜术语精度要求高（医疗，✅ B）｜**需要服务人工核对（✅✅ 只有 B）**｜不需要低延迟（✅ B）｜检索兜底已有混合检索（可与 D 组合）。→ **指向 B 为主、E 兜底、D 留作后续**。

## 6. 对 minicare-platform/api 的方案建议

### 6.1 总原则（一句话）

> **译文作为"一等辅助产物"存在：块级双语对（原文为准、译文为辅），生成于管线内、服务于人工核对与检索增强、消费于 LLM 上下文；原文永久保留，所有对齐、校验、引用链路不动。**

### 6.2 P1：新增 `translate` 步骤（块级双语对）

**步骤位置**：`segment → validate → **translate** → index`（validate 仍对原文跑数字校验，语义不变；index 改依赖 translate，链路自动继承 validate 的屏蔽状态）。

**产物**：`translate.json`，结构（示意）：

```json
{
  "kb_id": { "zh": "……译文……", "quality": "mt", "glossary_hit": ["eHF", "乳糖"], "model": "…", "created_at": "…" }
}
```

- 与 `segment` 产物**按块 1:1 对齐**（用块 id 作键，不做句级对齐）——人工核对场景块级已足够，避免引入新的对齐机制。
- 参考文献块等"默认排除检索"的块可配置跳过翻译（省成本）。
- 表格 / 数字 / 剂量：**数字与单位原样保留**，仅翻译表头与单元格文字（对齐 Hoverbot 的实体保护原则）。

**缓存与失效**（沿用项目铁律 #5）：
- `default_params` 增加 `translator=llm@v1` + 模型名 + **`glossary_hash`**。
- 改术语表 → 只重翻（不重跑 parse/segment）；改切块 → translate 自然失效重翻；改翻译模型 → 只重翻 + 重跑 index。
- 绝不触碰 `platform.version`。

**术语表**：`config/glossary.yaml`（或数据文件），中英对照起步：CMPA、eHF、AAF、casein、lactose 等。规则：术语表命中 > 模型自由翻译；表内规定"保留英文/双语"的词（如缩写、配方代号）强制保留。

**人工修正**：译文修正走 `edits/` 同型人工产物层（新 overlay，键为块 id），修正后 `quality: reviewed`，与现有切片编辑机制并列。UI 打标区分 `mt` / `reviewed` / `human`。

**前端**（已有页面的增强，不新增页面）：
- 「解析对照」「切片对照」两处加**双语视图开关**：英文文档默认显示译文，一键切原文；对照原文行号 / `block_is` 高亮机制完全复用（译文是附加属性，不参与对齐计算）。
- 机器翻译统一打标提示（"AI 翻译，仅供参考，以原文为准"）。

**检索侧（分两步走）**：
- 第一步（随 P1 或紧接 P1）：`index` 将**译文**作为第二索引字段（向量 + FULLTEXT 均可），中文查询走译文通道，英文查询/术语查询仍可命中原文通道（FULLTEXT ngram 对英文同样有效）。
- 第二步：按 §6.3 实测数据决定是否需要更激进的重排。

**LLM 消费侧**：minicare-agent 拼装上下文时，英文块给"译文为主 + 原文标题/术语保留"；引用格式仍锚定原件（文件名 + 页码），**引用不指向译文** —— 防止"引了一处翻译错误"。

**影响面清单（开工时同步核对）**：
`registry.py`（步骤表）｜`orchestrator.default_params`（翻译参数哈希）｜`src/lib/steps.ts`（六步状态推导唯一口径 → 变七步）｜前端工作台步骤条 / 产物面板｜`KB-CONTRACT.md`（产物契约）｜minicare-agent `search-knowledge.js`（上下文拼装）｜gotchas 文档（新增踩坑节）。

### 6.3 P2：跨语言检索评测（先测再改索引）

行业一致做法：**逐语言 / 逐场景评测，不用聚合数字下结论**。本项目：

1. 在 45 题回归集上**扩充 10–15 条跨语言题**，三类各若干：
   - 中文口语问法 → 英文文档（"奶粉里的乳糖是干嘛的"）；
   - 中英混合术语（"eHF 和 AAF 的区别"）；
   - 同一概念多种中文表达（"深度水解 / 完全水解 / 氨基酸配方"）。
2. 对照三组索引供给：**原文索引（现状） / 译文索引 / 双语索引**，观察召回差异。
3. 结论落地：若译文索引显著提升 → 固化；若无显著差异 → 翻译降级为"仅 UI + 消费层"（省掉索引侧改动）。

### 6.4 P3：可选项与推翻条件

| 选项 | 触发条件 | 推翻条件（不做/回退） |
|---|---|---|
| C 查询期翻译 | P2 实测发现"译文索引对**英文风格查询**（术语、缩写）受损"，需查询侧补翻 | 查询翻译引入新的术语失真（中文社区反复警告）时停用 |
| D 换多语言 embedding | 语料语言扩展到 3+ 种，或 B 路线维护成本失控 | 重测 97.8% 基线不达标（S-3 选型反弹）即回退 |
| 全量翻译退役 | — | 若 LLM 消费侧与人工核对都证明"不需要译文产物"（例如人工培养出英文阅读习惯）——但按当前三触点需求，该条件不成立 |

### 6.5 反模式清单（做什么之前先记住不做什么）

1. ❌ **解析前翻译** —— 毁版式、毁对齐、毁溯源，行业无此做法。
2. ❌ **译文覆盖原文** —— 永远双语并存；原文是唯一可引用、可校验、可审计的事实源。
3. ❌ **无术语表的裸机翻进医疗语境** —— 术语表 + 保留清单（缩写/剂量/配方代号）是底线。
4. ❌ **让翻译参与切片对齐计算** —— 对齐链只属于原文；译文是"挂"在块上的属性。
5. ❌ **让 LLM 二次改写译文**（QTT-RAG 的教训：重写引入事实失真与幻觉）—— 不确定就降级展示原文。
6. ❌ **不做评测就上索引** —— 45 题基线的口径必须扩完跨语言题后才动检索。
