## 11. 非目标 (Non-Goals)

| # | 不做的事 | 原因 |
|---|---|---|
| 1 | **替代医生做转奶决策** | 分型、严重度、是否需要 OFC 属医生判断 |
| 2 | 输出药物剂量、OIT/生物制剂方案、急救操作 | 医疗行为，属越界 |
| 3 | 自动"帮宝宝决定"能不能吃某食物 | 只给基于记录的判断依据与风险提示，最终裁定权在医生/家长 |
| 4 | 品牌与商品推荐（具体奶粉品牌/链接/购买） | 品牌中立是项目既定原则 |
| 5 | 与其他宝宝横向对比、排名、生长百分位"炫耀/焦虑"叙事 | 敏宝家长敏感度高 |
| 6 | 引入强化学习做策略优化（本期） | 数据量不足；先用规则版 JITAI，积累数据后再评估 |
| 7 | 更换现有小程序的**医疗档案结构** | **记录表单不在其列**：本版需要给表单加计划预填、内嵌语音入口、建议卡参数接收（见 [§7.6](02-能力设计.md)、[§8.3](04-实施派工.md)）。医疗档案重构见 PRD-005。 |
| 8 | 语音播报/音箱渠道上的计划推进 | 音箱渠道（PRD-004）本期只覆盖查询与记录 |
| 9 | 过敏原检测结果解读、化验单识别 | 属医疗判断，且识别可靠性不可控 |
| 10 | 疫苗等非过敏类长期计划 | 本版本聚焦转奶与排敏两条主线 |

## 13. 约束与风险

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| R1 | **机制分型缺失或填错** | 家庭阶梯给到 IgE 宝宝 → 严重过敏风险 | P0 设为阻断项；未填不得生成计划；分型变更时自动暂停计划 |
| R2 | 转奶算法参数取错（勺数/奶量） | 剂量错误 → 症状复发 | 参数全部取自真实记录，无记录必须人工确认，**禁止模型估算** |
| R3 | 家长误把"轻微变化"当失败而放弃 | 计划中断、信任受损 | 分级矩阵明确"轻微可继续"；文案避免"失败"表述 |
| R4 | 记录依从性衰减 | 计划停滞、指标失真 | 规则版 JITAI（每日 1 次上限）+ 一键打卡 + 计划可暂停 |
| R5 | 生产库迁移 020 未应用 | 疫苗窗口查不到、体检第 6 项不可用 | 第 6 项标记"待确认"并降级，不阻塞其他项；020 上生产后自动启用 |
| R6 | 时延回退（画像 + 计划查询） | 对话变慢（现 4.3-6.8s） | 服务端聚合 + 5 分钟缓存；工具结果精简；单轮工具调用上限不变 |
| R7 | 成本单价不准 | 账本数字失信 | 使用"档位级参考价"并标注"按常见价位估算"，不指向品牌 |
| R8 | 越界输出（模型绕开护栏） | 医疗风险 | 出口校验（服务端拦截）+ 漏报事件记录与抽检 |
| R9 | 计划过于复杂导致家长看不懂 | 弃用 | 每日只呈现"今天这一件事"；完整计划折叠；专业术语全部家长语言化 |
| R10 | 数据陈旧被当作阴性 | 误判"可以转奶" | 区分"无记录"与"数据陈旧"，带覆盖率标注，必要时转为对话确认 |
| R11 | 归一化误合并（如米粉 vs 小米粉） | 可吃清单计数错误 | 白名单 + 低置信度条目请家长确认，不自动合并 |
| R12 | 与医生意见冲突 | 家长困惑、信任受损 | 所有建议标注"以医生评估为准"；提供复诊摘要把冲突点显性化 |
| R13 | **感知误判：把"数据陈旧"当"无症状"** | 误判具备转奶条件 → 过早转奶 | 三态输出（有效结论 / 信息缺失 / 数据陈旧）+ 覆盖率限定（<50% 不下阴性结论）+ 必要时转对话确认（[§4.6](02-能力设计.md)） |
| R14 | 感知层失败或降级 | 画像为空 → 模型退回"什么都不知道"，给出与宝宝无关的建议（如默认母乳） | 单组失败仅该组标 `degraded`，其余照常注入；全量失败走保守默认；「已停母乳的宝宝被建议母乳喂养」列为最高优先级缺陷（[§4.6.3](02-能力设计.md)） |
| R15 | 主动提示变报告式输出 | 破坏对话感，家长不再阅读 | 单轮最多 1 条 + 同 flag 7 天去重 + 强提示白名单（[§4.5](02-能力设计.md) 频控规则） |
| R16 | 阶段判定被模型改写或三端不一致 | 首页说"可体检"、对话说"再等等"，信任受损 | 判定只在服务端产生，模型仅负责表述；[§4.9](02-能力设计.md) 验收含"三端结论一致"用例 |

## 14. 决策确认与待确认项

### 14.1 本版本已做的关键假设（待评审确认）

| # | 假设 | 若否，则 |
|---|---|---|
| A1 | 转奶采用**中国指南的 7 天第一瓶奶转换法 + 200ml 临界点**作为主算法，iMAP 六阶作为 1 岁后/已耐受 eHF 的延伸路径 | 需改为以 iMAP 为主，则数据模型要从"勺数配比"改为"食物形态阶" |
| A2 | 里程碑为 M0-M6 七级，且**回退不回滚已达成里程碑** | 需重新定义进度的心理模型 |
| A3 | 排敏 / 转奶**互斥**、且优先转奶 | 若允许并行，需要重新设计归因与冲突检测 |
| A4 | 耐受维持阈值采用"每周 2-3 次暴露" | 需依临床口径调整 |
| A5 | 本期不引入强化学习，用规则版 JITAI | 需提前引入数据采集与实验框架 |
| A6 | 成本按"档位级参考价"估算、不指向品牌 | 若需精确，需要家长手动录入购买单价 |
| A7 | 新增字段走 migration 022、新增表走 023（编号待确认） | 需与 020/021 的排期协调 |
| A8 | 状态感知走**服务端聚合 + 5 分钟 TTL 缓存**（约 7 条 SQL），模型不自算信号 | 若改为模型侧推断，需接受时延上升与结论不一致（[§4.8](02-能力设计.md)） |
| A9 | 首版信号范围＝P0 组（A/B/C/D/E/I/J），F/G/H 逐次补齐 | 若要求一次到位，需先解决 020 上生产与 F 组覆盖率（大便性状 22%）问题 |
| **A10** | 产出分为**数据类 / 内容类 / 建议类**三类，落库路径各不相同（[§3.3](02-能力设计.md)） | 若不分，则需要为"对话能否写库"反复开例外 |
| **A11** | **界面是唯一的记录写入路径**，agent 零写入（[§1.3](README.md) 硬原则 2） | 若允许对话写入，需接受同一份数据两条入口必然分裂 |
| **A12** | 语音录入以**独立 HTTP 接口**运行，不进对话会话（[§7.6](02-能力设计.md)-③） | 若与对话共用会话，语音将进入 transcript 与评估链路，且难以控制"不落库" |

### 14.2 待确认项（阻塞开发的）


1. **机制分型的采集能否落地**：家长能否说清 IgE / 非 IgE？是否需要"我不确定"→ 引导查看化验单/医生诊断的辅助流程？（影响 US-21 的交互设计）
2. **计划的载体**：今日行动卡放首页（与日记卡并列）还是新建"计划"Tab？涉及小程序导航结构调整。
3. **线下配合**：是否需要"家长打印/截图给医生确认"的固定流程（即医生在场确认后才能解锁下一阶）？
4. **US-29 账本**是否允许家长手动录入实际购买价格（提高精度 vs 增加负担）。
5. **主动推送**是否本期就上（依赖小程序订阅消息授权与用户教育）。
6. **评估方式**：长程指标（阶次推进率）的验证周期很长，首版验收是否接受"规则合法性 + 单案例端到端走通"作为替代？
7. **感知层的显性程度**：信号只在对话内生效，还是首页 / 里程碑页也显性展示"当前阶段 + 需要注意"卡（见 US-33 线框图）？涉及小程序首页信息密度与导航。
8. **提示频控阈值**：单轮 1 条 / 同 flag 7 天去重是否过松或过紧？强提示「可打断当前话题」的权限边界在哪，尤其 flag #1（过敏食材仍在食用）？
9. **对话入口的地位**：是继续放在 FAB 菜单（辅助入口），还是把"问助手"提升为 TabBar 一级入口？会改变首页信息密度与导航结构，且与第 7 项耦合。
10. **预填的默认力度**：转奶期喂养表单预填是"默认勾选"还是"仅提示"？前者省事但可能被误确认（记录失真），后者安全但多一步。
11. **建议落卡的呈现位置**：建议是出现在**对话内的卡片**（点"去处理"→跳界面），还是**直接出现在对应页面**（如排敏详情页出现"待采纳建议"条）？前者链路短、后者发现性好，也可两者都做。
12. **语音入口形态**：保留"长按 FAB"并新增记录页内嵌麦克风，还是把长按 FAB 改成"按住说话"的独立按钮（解决与"开菜单"手势冲突）？
13. **语音与症状描述的关系**：语音描述症状（"身上有几颗红点"）既是记录也是分级输入——是否允许"语音录入后自动触发一次分级**建议**"（仍不写库、仅出建议卡）？
14. **排敏语义的语音支持**：把 `food_observation` 纳入 `recordType` 需要扩充 NLU 提示词与 23 条回归集；"今天吃了小米粉没有反应"如何映射到打卡与 `severity`，需定义映射表。
15. **`paused` 与 `retry_after_date` 的产品语义**：`paused` 是"家长暂停"还是"系统挂起"？前者应进入 US-32 的可调整项，后者应进入 [§4.4](02-能力设计.md) 判定表的 `cooldown` 路径。
