### 2.2 六个被低估的现成资产（不要重造）

1. **打卡四动作已经是跨表状态机的雏形**：`detail.tsx` 的 `continue / pause / mark_suspected / mark_allergic` 直接映射 `food_observation_log.action`，并已联动 `health_record`（`createReaction`）。"反应分级处置"不需要新表，只需要**把选择权从家长手里接到 agent 手里**（见 [§5](02-能力设计.md)-D）。
2. **RemindersColumn 已经是"今日行动"的渲染器**：它已经会算"该喂奶了/预计 X 后喂奶/尿布进度"，有等级、有动作按钮、有进度环。缺的不是 UI，而是**数据源**（现在来自前端推导，应改为服务端计划）。
3. **排敏任务本身就是计划实体**：有 `observation_days`（DTO 限 3-7）、`current_day`、`retry_after_date`。这意味着待建的 `food_intro_plan` 与它**高度重叠**（见 §10-③）。
4. **生长曲线可直接当"事实展示层"**：不需要 agent 生成图，曲线上叠加"转奶事件 / 皮疹事件"标记即可（agent 只负责讲因果）。
5. **日记/语音已经验证了"agent 产出 → 界面确认 → 才落库"的模式**：日记是"对话生成 → 用户确认 → 落 `baby_diary`"；语音是"抽取草稿 → 结果面板确认 → 跳记录页预填"（`TabBar.tsx:304`）。**两条链路都没有绕过界面写库**——这正是本文档要固化的原则，不是要新建的做法（见 [§3.4](02-能力设计.md)）。
6. **语音录入链路已完整**：10 类记录的结构化抽取、五态结果面板、23 条回归用例（[§7.6](02-能力设计.md)）。录入效率的优化有现成地基，不需要从零做 ASR。

### 2.3 四个必须厘清的边界问题

| # | 问题 | 具体表现 | 结论 |
|---|---|---|---|
| ① | **两套"今天该做什么"** | `dashboard/RemindersColumn.tsx` 前端派生 vs 服务端 `get_today_actions` | 同一时刻首页说"该补打卡"、对话说"可做转奶体检"（R16）。**必须收回前端派生** |
| ② | **分析产出没有回程通道**（重新定义） | `minicare-agent/src/lib/tools/index.js` 四个工具全只读（`search_knowledge`/`query_baby_data`/`analyze_baby_data`/`generate_diary`）——**只读是对的**；但 agent 说"建议标记为轻微反应并降量"之后，家长只能自己回记录页找入口 | **缺的不是写能力，是"建议落卡"**（[§7.3](02-能力设计.md)） |
| ③ | **同一逻辑两份实现** | 分位数：`minicare-mp/src/lib/growth-standards.ts`（前端）+ `minicare-agent/src/lib/growth.js`（agent 复制）；排敏进度：首页 `AllergyProgressBar` + agent 聚合 | 两端结论必然漂移；且 iOS/JS 两端插值实现差异会放大 |
| ④ | **口径不一致** | 小程序排敏是**五态**（含 `paused`，`api/foodObservation.ts:3`），而部分文档仍写**四态**；待建的 `food_intro_plan` 与现成 `food_observation` 重叠 | 文档与实现各说各话，实施时必然返工 |

## 10. 需要先收敛的技术债（否则协同必然漂移）

| # | 债 | 现状 | 处置 |
|---|---|---|---|
| ① | **分位数两份实现** | `minicare-mp/src/lib/growth-standards.ts` + `minicare-agent/src/lib/growth.js` | 下沉服务端一份，两端取同源；agent 不再复刻（[§4.9](02-能力设计.md) 已要求"不得出现两套结论"） |
| ② | **排敏口径四态 vs 五态**（实为**口径收敛**，非数据迁移） | 枚举层**已经五态**：服务端 `ObservationStatus` 含 `PAUSED`、前端 `api/foodObservation.ts:3` 与 `lib/constants.ts` 均已含 `paused`；列类型是 `VARCHAR(20)` 而非 ENUM，**存量数据零修复** | 只剩三件事：① DB 列/表注释仍写四态 → migration 022 `MODIFY COLUMN ... COMMENT`；② `paused` 现渲染为「**已停用**」，与 PRD/agent 的「已暂停」口径不符 → 统一为「已暂停」（否则模型会顺着说成"这食物以后别吃了"）；③ 明确活跃集合＝`{observing}`、可恢复＝`{paused}`、终态＝`{safe, suspected, allergic}`。详见 [TECH-013](../../tech/TECH-013-state-awareness-implementation.md) §7.8 |
| ③ | **`food_intro_plan` 与 `food_observation` 重叠** | 后者已有 `observation_days`/`current_day`/`retry_after_date`/`severity` + 逐日日志 | **改为扩展 `food_observation`**（加 `normalized_name`、`plan_seq`、`planned_start`、维持期字段），**不新建平行表**，避免双写与口径分裂 |
| ④ | **DATE 序列化** | DATE 列表出参为 ISO 串（`2026-09-18T16:00:00.000Z`） | 对外一律 `YYYY-MM-DD`，走 `date.util.ts::formatSqlDate()`（两端展示都要过这层） |
| ⑤ | **生产库停在 migration 019** | `vaccine_*`/`checkup_*` 无字段 | 020 上生产后才能做复诊闭环（[§5](02-能力设计.md).F），此前医疗相关只能给计数并降级 |
| ⑥ | **语音 NLU 配置与前端类型枚举不对齐** | 前端 `VOICE_QUICK_TYPES` 含 `allergy`，后端 `recordTypes` 无此类型 | 收敛为单一配置源（后端 `VOICE_NLU_CONFIG` 为准），前端枚举由其派生 |
