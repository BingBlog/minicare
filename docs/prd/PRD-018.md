## 0. 结论摘要（TL;DR）

**一句话**：给首页「补剂 & 营养素」提醒条引入一个**宝宝级的每日补充计划**（显式配置项，配置在营养素记录页），提醒逻辑从「昨天吃了什么 → 今天没吃就催」改为「**今日记录 vs 计划清单 → 差什么催什么**」。

- **为什么做**：现口径「昨日反推」有两处不成立——① 家长昨天偶然吃过一项（如临时益生菌），今天就被催；② 真正每天要吃的项（如维生素 D）如果昨天恰好漏记，今天反而没有提醒。「要吃什么」应该由家长显式设定，而不是由历史记录推测。
- **怎么做**：① `baby_profile` 加一列 `supplement_plan`（JSON key 数组，migration 028）；② 营养素记录页（`feeding?tab=supplement`）新增「每日补充计划」折叠配置区（形态 A）；③ 首页补剂条改为对账差集展示（全吃完才隐藏；部分吃完提示剩余未吃项）。
- **零新增端点**：读走既有 `GET family/:fid/baby` 出口加字段；写走既有 `PATCH family/:fid/baby/:babyId`（**实测该端点权限为 `@MinRole(MEMBER)`，成员账号即可配置**）。
- **实测数据支撑（dev 库 247 条补剂记录，2026-10-12）**：key 分布 `vitD 112 / vitAD 74 / probiotic 23 / iron 19 / other 14 / probiotics 2 / calcium 2 / dha 1`——存在历史变体 `probiotics`，对账需 key 归一化（§3.4）。
- **不改什么**：表单记录流程 / dashboard 快捷录入 / agent 依从性信号 / Web 端，全部保持现状。

## 1. 背景与问题

### 1.1 现状口径（a439ceb，「昨日反推」）

首页补剂条现状（`SupplementBar.tsx`）：

| 今日 | 昨日 | 展示 |
|------|------|------|
| 有任一补剂记录 | — | 不展示（提醒目的已达成） |
| 无记录 | 有记录 | 「今天还没吃 · 昨日：维生素 D、益生菌」 |
| 无记录 | 无记录 | 不展示 |

### 1.2 问题

1. **被偶发项误导**：昨天临时吃过益生菌/锌，今天就被催补，而家长本意可能只是一次性给药；
2. **漏记即失提醒**：每天应吃的维生素 D，若昨天恰好没记（而不是没吃），今天反而不提醒；
3. **没有"应该"的概念**：系统没有宝宝的应吃清单，"今天要吃哪些"无从谈起，差集更无从算起。

### 1.3 本 PRD 的答案

引入**每日补充计划**（家长显式配置的应吃清单）作为唯一事实源，提醒 =「计划 − 今日已吃记录」的差集。**废弃「昨日反推」**。

## 2. 方案总览

### 2.1 判断逻辑：前后对比

| | 现状（昨日反推） | 新（计划对账） |
|---|---|---|
| 数据来源 | 昨日/今日**记录** | 宝宝**计划**（`supplement_plan`）+ 今日记录 |
| 命中逻辑 | 今日有**任意**一种记录 → 隐藏 | 计划内**全部**已吃 → 隐藏；否则列出未吃项 |
| 文案 | 「今天还没吃 · 昨日：xxx」 | 「今天还没吃：维生素 D、铁剂」（计划差集） |
| 无基线时 | 今昨都无记录 → 不展示 | 未配置计划 → 引导条（§3.5） |

> 语义升级说明：`a439ceb` 的"今日已吃 → 不展示"从"吃了任意一种"升级为"**清单内全部吃完才不展示**；部分吃完会提示剩余未吃的项"。

### 2.2 用户旅程

1. **一次性配置**：家长在营养素记录页展开「每日补充计划」，勾选如 [维生素 D、铁剂] → 保存；
2. **日常静默对账**：首页补剂条每天自动对比今日记录——没吃全 → 「今天还没吃：铁剂」；全吃完 → 条消失；
3. **调整**：宝宝月龄/医嘱变化时，回记录页改勾选即可（随时可改，改完即生效）。

### 2.3 与既有机制的关系

- **提醒开关**（`reminderSettings.supplement`，"我的 → 首页提醒"）：继续作为整条的显隐总开关，与计划互不冲突（关掉 → 计划/引导均不显示）；
- **与 PRD-009 同构**：日程 = 计划模板 + 首页 Bar 对账（已完成/跳过/错过）；本功能 = 补剂计划 + 首页 Bar 对账。"排一次、连续沿用、只在主动调整时变"的心智一致；
- **单一真相源**：计划存服务端宝宝档案（家庭内共享、换设备不丢），首页/记录页/（未来）agent 读同一份。

## 3. 详细设计

### 3.1 数据模型

`baby_profile` 加列（**migration 028**，`allergy_types JSON` 同表同模式先例）：

```sql
ALTER TABLE baby_profile
  ADD COLUMN `supplement_plan` JSON NULL
  COMMENT '每日补充计划：营养素 key 数组，如 ["vitD","iron"]；NULL=未配置';
```

- **数据形态：keys 数组**（如 `["vitD","iron"]`）——label 不入库，展示时由前端 `suppItems` 映射（未知 key 兜底原样显示），对账只用 key。选 keys 数组而非 `[{key,label}]` 对象数组：DTO 校验最简（`@IsIn(白名单, {each:true})`）、无冗余。
- 顺序：前端提交时按 `suppItems` 原顺序规范化，避免顺序抖动。
- 清空 = 存空数组 `[]`（与 NULL 等价视为"未配置"）。

### 3.2 记录页配置区（形态 A：入口行 + 配置区）

**位置**：`pages/records/feeding/index.tsx`，营养素 tab（`tab=supplement`）内、`SupplementSection` 上方；**仅新建模式（`!isEditMode`）渲染**（编辑历史记录时不出现配置区）。

**形态**：折叠节（默认收起）

- **收起态**（入口行）：「每日补充计划」+ 摘要（"未设置" / "维生素 D、铁剂"）+ 右箭头；
- **展开态**：8 项勾选列表（复用 `suppItems` 的 label + hint，勾选样式与表单一致）+ 说明小字（"配置后，首页会提醒今天还没吃的项"）+「保存计划」按钮；
- **保存**：本地暂存态 → 点击保存 → `PATCH baby { supplement_plan }` → 成功 toast「每日补充计划已保存」+ 更新页面态与 `minicare_baby` 本机缓存 + 自动收起；失败 toast 错误、保留编辑态。
- **初始值**：页面 `init()` 已有的 `babyApi.get(fid)` 出口直接带 `supplement_plan`（**零新增请求**）。

**清单范围（v1）**：仅预设 8 项（`suppItems`：维生素 D / 铁 / 钙 / DHA / 维生素 AD / 锌 / 益生菌 / 维生素 C）；表单里的「其他」自定义项**不进计划**（对账匹配不可靠，见 §7-③）。

### 3.3 首页提醒条（对账逻辑）

数据流：`refreshTodayRecords` 拉到的 baby（含 `supplement_plan`）+ 今日记录 → `SupplementBar{ planKeys, todayRecords }`。

判定：

```
plan 为空           → 引导条（§3.5，按决策）+ 或静默
已吃集 = 今日记录提取的补剂 key（归一化后，§3.4）
未吃集 = plan − 已吃集
未吃集为空          → 整条不渲染（全部吃完）
未吃集非空          → 「今天还没吃：维生素 D、维生素 AD、铁剂」
                      （最多列 3 项，超出追加「，另有 N 项」）
```

- 标题仍为「补剂&营养素」，动作仍为「记补剂」→ 跳记录页（配置区就在该页，动线自然）；
- 吃计划外的项（如临时锌剂）不影响对账；
- 提醒开关（`reminderSettings.supplement`）关闭时，本条与引导条均不渲染。

### 3.4 对账匹配口径与历史 key 归一化（实测支撑）

**已吃集提取**：今日记录中 `feed_type='supplement'`（含历史数据 `complementary_food='营养素'`）记录的 `supplement_items`，取 `key` 去重。

**已知脏数据（dev 库实测）**：`probiotics`（复数，2 条）与 `probiotic`（23 条）并存；其余为 `vitD / vitAD / iron / other / calcium / dha`，形态干净。

**归一化规则**（新增单点函数 `src/lib/supplements.ts::normalizeSupplementKey()`）：

1. 特殊变体映射表：`probiotics → probiotic`（初始仅此一条，后续按实测扩展）；
2. 比较时统一小写（`vitd` ⇔ `vitD`）；
3. `other`（自定义项）不参与计划对账。

> 单一出处纪律：该映射表是唯一维护点；`SupplementBar` 的已吃集、未来任何对账消费方都必须经过它，禁止各自实现第二份。

### 3.5 未配置时的行为（§7-②，已采纳引导条）

- **建议 b（推荐）：轻引导条**——未配置且未关闭提醒开关时，在原位置显示灰调引导条：
  - 标题「还没有每日补充计划」；desc「设置每天要补的营养素，首页会提醒还没吃的」；动作「去设置」→ 跳记录页营养素 tab；
  - 与 PRD-009「还没有作息计划」引导条完全同构（同位置、同灰调样式）；配置完成后消失；
- 备选 a：静默不显示（最安静，但功能藏在记录页 tab 里、无发现路径，提醒功能对老用户等同于消失）。

### 3.6 权限与边界

- **写权限**：`PATCH family/:fid/baby/:babyId` 实测为 `@MinRole(MEMBER)`——**家庭成员（非 owner）也能配置**（补剂属日常照护，语义合理，无需改权限）；
- **多宝宝**：按 `baby_id` 独立（计划挂在各自档案上）；
- **并发**：低频配置（一次性动作），不做自旋/版本校验；后保存覆盖先保存（家庭内可接受）；
- **环境差异**：migration 028 先上 `minicare_dev`；staging / 正式随发布节奏（两库当前停在 019，见 minicare-dev SKILL 提醒）。
