### 阶段一：语料入库

> 阶段目标：把源文件可靠地收进来，并建立可溯源的来源台账。**这一阶段的产出是后续一切加工的输入。**

#### **US-01: 作为知识库维护者，我希望拖拽登记源文件并自动判重，以便于不重复入库同一份指南。**

*   **价值陈述 (Value Statement)**:
    *   **作为** 知识库维护者
    *   **我希望** 在一个界面里完成文件登记、自动判重、来源信息预填
    *   **以便于** 用最少的操作把语料收进平台，且不需要打开代码编辑器
*   **业务规则与逻辑 (Business Logic)**:
    1.  **前置条件**: 平台已启动且本机可访问；源文件在手（PDF 或 HTML）
    2.  **操作流程 (Happy Path)**:
        1. 我进入「文档库」，点「＋ 登记源文件」，拖入 1–N 个文件（也支持文件夹多选）
        2. 系统对每个文件流式计算内容哈希（sha256），作为唯一 ID 与判重依据
        3. 系统按「文件名规则 → 正文抽取」两级预填来源信息（来源名称、发布机构、年份、地区、证据级别、适用年龄、许可证），**抽不到的字段标 ⚠ 待补**
        4. 我核对预填结果，点「登记」
        5. 台账出现该文档，状态为「待处理」；**不自动开始处理**，等我在台账里勾选后统一触发
    3.  **异常处理 (Error Handling)**:
        *   **内容哈希已存在** → 弹出判重窗，显示首次登记时间、当前状态、切片数，以及**「被 N 个召回测试题引用」**；我必须选 `跳过` / `覆盖为新版本` / `并存为 v2` 三者之一，否则不产生任何新记录
        *   **选「覆盖为新版本」** → 旧版本标为「已归档」但**产物保留可查**；新版本进入「待处理」，并明确提示「该文档原有切片与向量已失效」
        *   **格式不支持**（如 `.docx` `.epub` `.ofd`）→ 明确拒绝，列出支持的两种格式（PDF / HTML），**不做任何登记**
        *   **同一批里自身重复**（我选了两次同一文件）→ 只登记一次，并提示"已自动去重 1 个"
        *   **磁盘写入失败 / 权限不足** → 明确报错，**不留半条记录**（登记是原子的）
    4.  **容量与性能提示**: 单文件上限待定（建议 ≤ 100MB）；批量登记不阻塞界面
*   **验收标准 (Acceptance Criteria)**:
    *   **场景 1: 正常登记**
        *   **GIVEN** 我手上有一份没登记过的 PDF 或 HTML
        *   **WHEN** 我拖入登记页并确认预填来源后提交
        *   **THEN** 系统登记成功，台账出现该行、状态为「待处理」，且**不自动开始处理**
    *   **场景 2: 完全重复**
        *   **GIVEN** 该文件的内容哈希已存在
        *   **WHEN** 我再次登记
        *   **THEN** 弹出判重窗并显示首次登记时间、当前状态、切片数与被召回测试题引用数；**在我选择三者之一前不产生任何新记录**
    *   **场景 3: 覆盖为新版本**
        *   **GIVEN** 判重窗已弹出
        *   **WHEN** 我选「覆盖为新版本」
        *   **THEN** 旧版本标「已归档」且产物保留可查，新版本进入「待处理」，并提示「该文档原有切片与向量已失效」
    *   **场景 4: 来源信息缺失**
        *   **GIVEN** 系统无法从文件名与正文推断出年份或证据级别
        *   **WHEN** 登记完成
        *   **THEN** 该字段在台账标 ⚠，且该文档**不能被发布**（发布前检查会拦下；~~卡在暂停点 1~~ 该机制已移除）
    *   **场景 5: 格式不支持**
        *   **GIVEN** 我选了 `.docx`
        *   **WHEN** 系统校验
        *   **THEN** 明确拒绝并提示支持的两种格式，登记列表中不出现该文件

#### **US-02: 作为知识库维护者，我希望台账能反映每份语料的来源完整度与合规状态，以便于溯源、合规与维护。**

*   **价值陈述 (Value Statement)**:
    *   **作为** 知识库维护者
    *   **我希望** 一眼看出哪些语料来源不全、哪些许可证未标注、哪些已被新版取代
    *   **以便于** 保证每条知识都能溯源到权威来源，并且在合规上不留空白
*   **业务规则与逻辑 (Business Logic)**:
    1.  **前置条件**: 台账中已有已登记语料（US-01 产出）
    2.  **操作流程 (Happy Path)**:
        1. 打开文档库，顶部看到**完整度摘要**：来源完整 N/总数、许可证未标注数、待补全数、已被取代数
        2. 点「仅看缺项」筛出待补全的语料，逐份补全字段
        3. 打开任一文档详情，看到**版本历史**（每次覆盖/并存产生一个版本）、**引用关系**（被哪些召回测试题引用、取代了谁/被谁取代）、**合规信息**（许可证、使用范围、MinerU 署名义务）
        4. 点「导出台账」得到含全部台账字段的 Markdown 表格文件
    3.  **异常处理 (Error Handling)**:
        *   **必填字段缺失** → ~~该文档卡在暂停点 1~~ **不影响跑六步**，但**不可发布**；台账与发布前检查两处都会标明缺哪一项
        *   **疑似同一来源**（新文件标题与已有文档高度相似但哈希不同）→ 登记后提示，允许建立「取代」关系；建立后旧文档自动标「已归档」且不可发布
        *   **台账与数据库不一致** → 以数据库为准重建台账，**不出现两份不一致的数字**（台账不是独立真相源）
        *   **台账导出失败** → 提示失败原因，不产生残缺文件
    4.  **留存约束（已知取舍）**: 台账**只存 DB，不进 git**（决策 §19 D-04），可追溯性依赖数据库备份；「台账定期导出到仓库」列为 P2 可选项（§18 R-01）
*   **验收标准 (Acceptance Criteria)**:
    *   **场景 1: 缺项拦截发布**
        *   **GIVEN** 台账中某文档「年份」为空
        *   **WHEN** 我尝试发布它
        *   **THEN** 拒绝发布并指出缺哪个字段，直接给出补充入口
    *   **场景 2: 零配置接入新语料**
        *   **GIVEN** 我登记一份从未出现过的新指南
        *   **WHEN** 预填完成
        *   **THEN** 来源名称 / 年份 / 地区三项至少被正确预填或明确标 ⚠，**且我不需要改任何代码或配置文件**
    *   **场景 3: 疑似同一来源**
        *   **GIVEN** 新文件的标题与已有文档高度相似但哈希不同
        *   **WHEN** 登记完成
        *   **THEN** 系统提示疑似同一来源并允许建立「取代」关系；建立后旧文档自动标「已归档」且不可发布
    *   **场景 4: 台账一致性**
        *   **GIVEN** 数据库里的切片数被外部脚本改过
        *   **WHEN** 我刷新台账
        *   **THEN** 台账以实际数据为准重建，不显示第二份不一致的记录
    *   **场景 5: 导出**
        *   **GIVEN** 台账有 20 份语料
        *   **WHEN** 我点「导出台账」
        *   **THEN** 得到包含全部台账字段的 Markdown 表格文件

#### **US-03: 作为知识库维护者，我希望一键跑通处理并看到步骤进度，失败时只重试那一步，以便于不再靠命令行猜状态。**

> **（2026-10-09 晚更新）**「处理进度」页**已下线**（用户要求：文档按篇处理、无队列场景）——
> 批量任务列表 / 取消 / 排队位置与端点 `/api/queue*` 一并移除；队列本体保留为 CLI（`kb-pipeline run --enqueue` /
> `queue [--resume|--cancel-all]` / `drain`）。单文档处理不受影响（「文档管理」卡片按钮 + 工作台 / 处理弹框看状态），
> 执行历史见工作台「处理记录」页签。下文中批量队列相关描述与线框图【B】仅存历史口径。详见 `06-开发进展与交接.md` §0。

*   **价值陈述 (Value Statement)**:
    *   **作为** 知识库维护者
    *   **我希望** 勾选文档就能一键处理，并实时看到 6 步状态与真实进度
    *   **以便于** 不再手工分步执行、不再靠日志猜"卡在哪了"
*   **业务规则与逻辑 (Business Logic)**:
    1.  **前置条件**: 语料已登记（US-01），状态为「待处理」
    2.  **操作流程 (Happy Path)**:
        1. 我在台账勾选 1–N 份文档，点「开始处理」
        2. 系统把它们加入待处理队列；**解析步骤可并发**，本地步骤（正文清洗/切块/校验/索引）串行
        3. 我在「处理详情」看到 6 个步骤横排：`① 预检 ② 解析 ③ 正文清洗 ④ 切块 ⑤ 内容复核 ⑥ 索引`，逐个变绿并显示各自耗时
        4. 当前步骤显示**阶段级进度**：如「解析中 · 已等待 1m42s」
        5. ~~全部完成后状态变为「待确认元数据」，给出暂停点 1 的入口~~
           → **改为（2026-10-09）**：六步跑完即达「已就绪待发布」，中途**无人工关卡**
    3.  **异常处理 (Error Handling)**:
        *   **某份解析失败** → 该文档标红、指出失败步骤与原因，**其余文档继续跑**；批量结束时不弹"全部失败"的误导提示
        *   **云端解析超时** → 可单步重试解析，**前置的预检不重跑**，日志显示「前置步骤已跳过」
        *   **处理中我关掉了平台** → 重启后从断点继续，已完成步骤产物不丢失、不重算
        *   **我中途取消** → 排队中的立即消失；执行中的在**当前步骤边界**停下并保留已完成步骤产物；**没有任何半成品被标为可用**
        *   **预检判定该文档是扫描件** → 自动把解析档位锁到含 OCR 的档位，**不再依赖手工维护的 OCR 文件清单**
    4.  **进度诚实性约束**: 云端只能轮询到任务状态，**拿不到页级进度**。因此界面只显示阶段 + 已耗时，**不出现会卡在 90% 的假进度条**
*   **验收标准 (Acceptance Criteria)**:
    *   **场景 1: 一键处理**
        *   **GIVEN** 台账中 3 份文档处于「待处理」
        *   **WHEN** 我勾选并点「开始处理」
        *   **THEN** 队列出现 3 条记录，步骤条逐步推进，全部完成后状态变「待确认元数据」
    *   **场景 2: 单份失败不中断整批**
        *   **GIVEN** 队列中有 5 份，其中第 2 份解析失败
        *   **WHEN** 处理继续
        *   **THEN** 第 2 份标红并给出失败原因，第 3–5 份照常跑完
    *   **场景 3: 单步重试**
        *   **GIVEN** 某文档卡在「解析失败」
        *   **WHEN** 我点「重跑此步」
        *   **THEN** 只重跑解析，前置的预检不重跑，日志可见「前置步骤已跳过」
    *   **场景 4: 断点续跑**
        *   **GIVEN** 处理到第 4 步时我关掉了平台
        *   **WHEN** 我重新打开

#### **US-12: 作为知识库维护者，我希望看到未命中问题形成的知识缺口，以便于知道下一份该补什么语料。**

*   **价值陈述 (Value Statement)**:
    *   **作为** 知识库维护者
    *   **我希望** 未命中的问题按主题聚合，并区分"真的缺语料"还是"切片有问题"
    *   **以便于** 补语料这件事从"靠猜"变成"按台账做"
*   **业务规则与逻辑 (Business Logic)**:
    1.  **前置条件**: 有回归未命中记录或线上未命中记录
    2.  **操作流程 (Happy Path)**:
        1. 打开知识缺口，看到按主题聚合的缺口列表：主题、来源（回归/线上提问）、出现次数、首次与最近出现时间、建议动作、状态（开放/已关闭）
        2. 展开某个缺口，看到命中该缺口的题目、库内现状（相关块数与最强相关块相似度）、建议补录的语料类型
        3. 我点「关联已登记语料」把补录的语料与该缺口关联，或点「标记为暂不处理」（需填原因）
        4. 补录语料并发布后，下次回归命中 → 该缺口**自动标为已关闭**
    3.  **异常处理 (Error Handling)**:
        *   **归因区分（关键）**：未命中题若其 gold 块**其实存在但被排除检索**，应归因为「切片/排除问题」并给出**跳转「内容校对」页的入口**，**不误报成"语料缺失"**；若相似度低于该主题均值，才归因为「覆盖缺口」
        *   **同一主题反复出现** → 出现次数累加并**提升优先级**
        *   **缺口长期悬空** → 允许「标记为暂不处理」并必须填原因，避免台账堆积无意义条目
        *   **缺口来源为线上提问** → 只记录查询文本与命中统计，**不记录用户身份、家庭数据、会话内容**（§9.4 隐私边界）
    4.  **闭环价值**: 这条故事把「线上/回归发现问题」→「语料补充」→「下次回归验证」连成闭环，是平台自我改进的机制
*   **验收标准 (Acceptance Criteria)**:
    *   **场景 1: 缺口聚合**
        *   **GIVEN** 连续两次回归中 A-04 都未命中
        *   **WHEN** 我看缺口台账
        *   **THEN** 该缺口出现次数为 2 且标注优先级提升
    *   **场景 2: 区分覆盖缺口与切片问题**
        *   **GIVEN** 未命中题的 gold 块其实存在但被排除了检索
        *   **WHEN** 系统分析
        *   **THEN** 归因为「切片/排除问题」并给跳转「内容校对」页的入口，**不误报成「语料缺失」**
    *   **场景 3: 补录后自动关闭**
        *   **GIVEN** 我补录了过敏进程相关语料并发布
        *   **WHEN** 下次回归命中
        *   **THEN** 该缺口自动标为已关闭并留痕
    *   **场景 4: 暂不处理须填原因**
        *   **GIVEN** 我点「标记为暂不处理」
        *   **WHEN** 原因为空
        *   **THEN** 不允许提交

#### **US-13: 作为 Agent 维护者，我希望冻结切片字段契约并观察线上检索，以便于平台改动不打挂智能体。**

> **（2026-10-09 晚更新）**「智能体对接」KB 侧页面**已下线**（用户要求；知识库对接 Agent 的测评由「Agent 测评」域覆盖）——
> 契约校验与线上观察保留为 CLI（`kb-pipeline contract show/validate/observe`）与 `KB-CONTRACT.md`；
> 下文中「页面」相关描述仅存历史口径，能力规格仍以 CLI / 契约文档为准。详见 `06-开发进展与交接.md` §0。

*   **价值陈述 (Value Statement)**:
    *   **作为** Agent 维护者（同一人，另一个角色）
    *   **我希望** 检索响应结构与语义约束被固化并在发布时自动校验
    *   **以便于** 平台侧改字段、改过滤语义时不会静默打挂 `minicare-agent`
*   **业务规则与逻辑 (Business Logic)**:
    1.  **前置条件**: 平台与 `minicare-agent` 各自独立演进
    2.  **操作流程 (Happy Path)**:
        1. 「智能体对接」页展示当前冻结的**响应结构、条目字段、过滤参数、语义约束**与版本号及变更记录
        2. 我改动字段或语义时，先更新契约文档（记变更记录 + 递增版本）
        3. 发布时**自动执行契约校验**，通过才允许发布
        4. 同时展示**线上检索观察**：近 7 天检索次数、命中/未命中数、低分数、未命中 TOP
        5. 未命中 TOP 可**一键记入知识缺口**（打通 US-12）
    3.  **异常处理 (Error Handling)**:
        *   **契约校验失败**（如把 `risk_level` 从响应里删掉）→ **阻断发布**，指出缺了哪个字段或哪条约束失效
        *   **语义约束失效**（如被排除块又开始返回）→ 校验失败并阻断
        *   **向量维度不一致** → 校验失败并提示需全量重嵌入
        *   **检索日志写入失败** → **不影响用户问答**（旁路设计）；日志侧记录失败原因，不重试到阻塞主链路
        *   **契约与实际实现漂移**（我改了实现没改文档）→ 校验以**实现行为**为准，发现不符即失败
    4.  **契约 v1 内容**（决策 §19 D-20，对齐 `search-knowledge.js` 现状）:
        - 响应结构：`found` / `items[]` / `topK`
        - 条目字段：`id` · `kb_id` · `title` · `content` · `content_truncated` · `source` · `risk_level`
        - 过滤参数：`query` · `riskLevel` · `category`
        - 语义约束：① `retrieval_status != 'enabled'` 的条目永不出现 ② `content` 超 800 字截断并标记 ③ 未命中返回明确的未找到结构
    5.  **为什么必须自动校验而不只是写文档**: `minicare-agent` 与平台是两个独立项目，靠"记得同步"一定会漏；**契约校验是这条链路上唯一的自动化保险**
*   **验收标准 (Acceptance Criteria)**:
    *   **场景 1: 契约校验拦下破坏性改动**
        *   **GIVEN** 我把 `risk_level` 从响应里去掉
        *   **WHEN** 我尝试发布
        *   **THEN** 契约校验失败并阻断发布
    *   **场景 2: 日志旁路**
        *   **GIVEN** 检索日志写入失败
        *   **WHEN** 家长提问
        *   **THEN** 问答正常返回，不因日志失败影响用户
    *   **场景 3: 观察数据回流**
        *   **GIVEN** 线上有未命中提问
        *   **WHEN** 我打开该页面
        *   **THEN** 看到未命中问题的聚合，并能一键记入缺口台账
    *   **场景 4: 语义约束被校验**
        *   **GIVEN** 我把某个被排除的块错误地设为可检索
        *   **WHEN** 我发布
        *   **THEN** 契约校验发现「被排除块被返回」，阻断发布
