## 3. P0 级：核心矛盾（5 项）

### P0-1 G8/D5「单篇 LLM 调用 ≤ 3 次」与四触点成本模型在数学上不成立

**证据**：
- G8（§2.1）与 D5（§11.4）均要求"单篇 20 页论文 LLM 调用 ≤ 3 次"
- FR-4.4（P0）：每张图生成 VLM 描述；FR-10.6：L1/L2/L3/L4 四触点
- §6.1：`annotate_figures` 引擎为"规则 + VLM"，`repair_tables` 为"规则 + VLM"，`segment` 标注"✅ L4 可选"

**问题推演**：一篇 20 页医学论文典型含 4–8 张图。L2 每图至少 1 次调用 → 仅图片描述就 4–8 次，已超 3 次预算；L4（Contextual Retrieval）按 Anthropic 原文是**每 chunk 一次调用**，20 页按 FR-6.2 的 300–500 字子块切约 20–40 块 → 单触点 20–40 次。也就是说，只要 FR-4.4（P0 必做）生效，"≤ 3 次"在任何配置下都不可达；若为守住 3 次而关闭 L2，G7（图表可检索）和 D2 验收（命中率 ≥ 70%）又不可达。**两个 P0 目标互相锁死**。

**建议**：
1. G8 改为**预算制而非次数制**："单篇 LLM 成本可配上限（默认 ¥X / N 次调用），超限自动跳过非必需触点并告警"——FR-10.5 其实已经是这个形态，让 G8 与 FR-10.5 对齐即可
2. 在 §5.10 增加成本模型说明：L1 ≤ 1 次；L2 = 图片数 × 1；L3 = 校验失败表数 × 1；L4 = 切片数 × 1（默认关闭，按需开启）
3. D5 验收同步改为"预算内调用 100% 可追溯"（与 D6 合并）

### P0-2 NFR-10「不上传全文」与 L2/L3 的 VLM 部署位置矛盾——缺一条决策记录

**证据**：
- NFR-10：接外部 API 时只发 DOI/PMID，不上传全文
- FR-4.4/FR-5.1：图片描述与表格修复依赖 VLM；全文未提 VLM 跑在哪

**问题推演**：VLM 只有两个选择，且都有硬伤——
- **云 VLM API**（gpt-4o / qwen-vl / glm-4v 等）：图表图片必须上传。图片是文献内容的一部分，"只发 DOI/PMID"的承诺被打破。医学文献的版权敏感性虽低于全文，但 PRD 已有 NFR-11 合规意识，此处不应留白
- **本机 CPU VLM**：与 DEC-3（本机 CPU、无 GPU）叠加，30 张图的描述任务在 CPU 上效果与速度都存疑，且 PRD 未给本地 VLM 选型

**建议**：新增 DEC-10「VLM 部署位置」，二选一并回写：a) 云 VLM，NFR-10 改写为"元信息类 API 只发 DOI/PMID；VLM 触点允许上传图表裁切图，不上传整页/全文"；b) 本地 VLM，需在 P3 里程碑前完成选型验证（效果不达标则该条退回重议）。

### P0-3 §6.1 拓扑图与 §6.5 流程图的执行顺序互相矛盾，且状态派生规则在并行方案下会"遮蔽"暂停点

**证据**：
- §6.1：`normalize ─┬→ extract_meta ├→ annotate_figures ├→ repair_tables └→ segment`，并明确"步骤 5/6/7 互不依赖，可并行执行"
- §6.5 流程图：`C2 元信息确认（暂停点 1）→ D1 annotate_figures / D4 repair_tables`——图片与表格处理排在**人工确认之后**
- §6.2 状态派生：优先级第 1 条"任一步骤 running → 处理中"，第 3 条才是"停在 extract_meta 完成 → 待确认元信息"

**问题推演**：两种说法只有一个是真的。若按拓扑并行（更优——人看元信息表单时机器在干活），则 extract_meta 完成的瞬间 annotate_figures/repair_tables 大概率仍在 running，按 §6.2 优先级，文档状态永远显示"处理中"而非"待确认元信息"，**暂停点 1 在界面上不可见**，用户不知道该去确认了。若按流程图串行，则并行声明是错的，且白白浪费人工等待时间。

**建议**：
1. 统一为并行方案（体验最优）：修改 §6.5 流程图，C1 完成后同时分叉出"C2 人工确认"与"D1/D4 机器处理"，两路汇合于 D7（segment 前需 5/6/7 全部完成 + 元信息已确认）
2. 修改 §6.2 派生规则为："`extract_meta 完成 && meta 未确认 && 6/7 无 running` → 待确认元信息；`extract_meta 完成 && meta 未确认 && 6/7 running` → 处理中（附提示：元信息可先行确认）"

### P0-4 fast 档（pypdf）产物无法满足 `ParseArtifact` 契约——降级链路的数据兼容性缺失

**证据**：
- §7.2：`ParseArtifact.blocks` 要求带 `page + bbox + type`；`images` 为裁切图列表；`tables` 为 HTML 或裁切图
- FR-2.7：MinerU 不可用时自动降级 fast（pypdf）
- pypdf 的能力边界（§1.2 P4 自己也承认）：只能抽文字层，无 bbox、无表格 HTML、无图片裁切

**问题推演**：降级发生后，`ParseArtifact` 的 bbox/images/tables 字段无值可填。下游 `annotate_figures`、`repair_tables` 对 fast 产物执行会怎样？空转还是报错？FR-4.x/FR-5.x 全部以 MinerU 产物为前提，**降级文档的图片/表格机制完全未定义**——但降级是 P0 行为（FR-2.7），意味着 P0 主流程天然存在一条"产物残缺"的路径，G7 对降级文档不成立却没有任何豁免声明。

**建议**：
1. `ParseArtifact` 增加 `capabilities` 掩码字段（如 `{layout: true/false, table: bool, figure: bool, formula: bool}`），允许 bbox/images/tables 为空
2. 下游步骤按 capabilities 短路：无 figure 能力时 `annotate_figures` 直接产出空集并标记 `skipped_no_capability`
3. 新增验收豁免条款："degraded=true 的文档，G7/D1/D2/D3 指标豁免；文档列表须展示降级提示（已有 FR-2.7，补充图片表格不可用说明）"

### P0-5 NFR-1「standard 档 ≤ 3 分钟」与 R4「CPU 逐页数十秒」自相矛盾

**证据**：
- NFR-1：20 页纯文本层论文 standard 档 ≤ 3 分钟
- R4（自称"本期最高风险"）：CPU 上逐页 OCR 可能单页数十秒

**问题推演**：MinerU pipeline 后端对**每页**都要跑版面模型 + OCR 模型（不区分该页有无文字层，不做文字层复用）。按 R4 自己的量级：20 页 × 单页 5–30 秒（M 系列芯片差异大）= 100–600 秒，3 分钟是乐观情形的边缘值。PRD 用"纯文本层"限定条件并不能让 pipeline 跳过 OCR——这个指标建立在对 MinerU 行为的错误假设上。更麻烦的是：NFR-1 是 §11 验收的隐含依据，指标定错会连带 B4（校准时耗 ≤ 3 分钟）的可用性判断。

**建议**：改为"基准后承诺"（benchmark-then-commit）：
1. NFR-1 临时改为"以 P2 第一周 10 篇基准实测的 P50/P90 为准，正式指标在基准报告产出后回填"
2. 立即在 §12 的并行建议中加上基准任务："10 篇典型文献 × fast/standard 两档 × 记录单页耗时"，与 P1 并行（当前只提了脏样本集，没提基准计时）
3. 补充机型注记（Apple Silicon 具体型号），避免指标不可复现

## 4. P1 级：重要缺陷（8 项）

### P1-6 人工编辑 × 缓存 × 重切的交互语义未闭环——重切后编辑映射断裂

FR-1.11 说 `chunks.json` 与 `chunks.edited.json` 并存；FR-4.7/FR-5.10 说驳回/修正后重跑不被覆盖。但**用户改参数重跑 segment 后**：新 ChunkSet 的 chunk_id 全部重新生成，旧编辑（挂在旧 chunk_id 上）如何迁移？三种情形都没定义：a) 重跑 segment 时缓存命中（输入 hash 未变），人工编辑是否被绕过；b) 重切后 index 读哪个文件（编辑版还是机器版）；c) FR-7.4 的拆分/合并产生的"派生块"与原块的关系。**这是知识库建设中最经典的痛点，不提前定义，StepRunner 的接口设计就要返工**。建议：定义 `edit` 的存储层级（chunk_id 级 diff + 内容 hash），规定"重切后编辑默认失效、界面列出可找回的旧编辑"。

### P1-7 L4 触点违反自己定的 D8 原则——没有定义"不调用的条件"

D8 明确要求"每个 LLM 触点必须定义不调用的条件"，L1/L2/L3 都有（确定性优先/校验失败才修），唯独 L4（Contextual Retrieval）只在 §6.1 标了"可选"，触发条件、跳过条件、默认开关状态全部缺失。且 L4 开/关会改变 embedding 输入文本 → index 必须重跑，但 §6.3 失效传播表只覆盖"步骤重跑"，不覆盖"index 上游参数变化"。建议补齐：L4 默认关闭，开启条件 = B5 检索验证命中率不达标时的调优手段；开启后自动 invalidate(index)。

### P1-8 FR-7.14「导出校对后版本 Markdown」的重建机制未定义

人工编辑分散在 `chunks.edited.json`（切片文本）、`FigureNote.description/review_state`（图片）、`StructuredTable`（表格）三处，而 Markdown 是**线性文档**。从切片反向重建文档：切片间的顺序还原、被过滤图片是否包含、`excluded_from_retrieval` 的参考文献导不导、图片引用路径是产物内部路径还是拷贝到导出目录——全部未定义。这是 P0 需求，实现复杂度被明显低估。建议：明确导出来源 = `NormalizedDoc`（保持线性）+ 三类人工 patch 的应用规则，并把"图片导出目录结构"写进验收标准 D13。

### P1-9 中文支持停留在参数级，缺三个关键环节

a) **混合语言策略**：MinerU 的 lang 参数是全文级，"中文优先"对英文正文+中文摘要（或反之）的文档，会让英文页跑中文 OCR 模型，识别质量可能下降。需要逐页语言检测或接受降质并标记；b) **BM25 中文分词**（FR-9.2）：中文 BM25 必须分词（jieba 等），只字未提，直接影响中文检索；c) **embedding 模型中文能力**：全文未提 embedding 选型，若现有模型英文为主，中文切片向量质量堪忧。且 **D11/D12 只测解析侧，中文检索命中率没有验收指标**——建议加 D14"中文查询 top-5 命中率"。

### P1-10 v3.1 决策未同步到数据契约——残留引用至少 4 处

DEC-2（不做 JATS）与 DEC-3（high 不实现）已定，但：§7.1 `PreflightReport.pmc_available`（注释"是否有 JATS XML 可取"）应删除；`recommended_tier` 注释仍含 high；§6.1 parse 引擎列写"MinerU / JATS / pypdf"；§7.2 写"所有引擎（MinerU / pypdf / JATS）"。评审文档里这种残留会让实现者误判范围。

### P1-11 接口清单缺口：7 个已定义需求没有对应 API

§9 缺：Markdown 导出（FR-7.14，P0）、文档删除（FR-9.5，P0）、图片恢复被过滤项（§8.4）、切片禁用/删除（FR-7.5/7.6）、章节级重切（FR-7.8）、文件上传（FR-2.1"已有实现"也应在清单中标注沿用）、任务取消（见 P1-12）。

### P1-12 并发/队列/取消模型完全缺失

R4 应对②说"全部走后台任务"，但任务模型没有需求：批量上传 10 篇含扫描页文献（单篇可能 30 分钟+）时，parse 是串行还是并行（CPU 密集任务并行会互相拖慢）？排队优先级？**长任务没有取消机制**（用户发现传错文件只能干等）。建议新增 FR：单 worker 串行队列 + 任务可取消 + 前台显示队列位置。

### P1-13 引擎选型缺少 go/no-go 闸门

§12 建议 Docling 三方对比与 P1 并行，但 P2 里程碑直接就是"MinerU 接入"，前置条件没包含对比结论。若脏样本对比显示 Docling 显著更优，P2 返工。建议把"脏样本集对比报告"设为 P2 的准入条件（若 MinerU 胜出则放行，否则重议选型），写进里程碑前置列。

## 7. 审查人备注

这份 PRD 最大的优点是"决策留痕"，最大的风险也是"决策改了但正文没跟上"（P0-2/P0-3/P0-4/P1-10 全是这一类）。建议建立一条轻量规则：**每次 DEC 变更后，用关键词全文反查一遍受影响的 FR/NFR/数据契约/流程图**（如本次的 `JATS`、`high`、`pmc_available`、`并行`），把同步检查做进 PRD 的变更流程。对单人项目，这条规则 10 分钟就能执行一次，能避免绝大多数一致性问题。
