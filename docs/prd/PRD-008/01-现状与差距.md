## 2. 现状盘点：知识库现在到底是怎么建的（实测）

> **本节全部结论来自代码核对，不是转述文档。** 旧 v3 文档的最大问题就是描述了一个不存在的平台，因此本文的现状一律以代码为准。

### 2.1 五个环节与它们的真实实现

| # | 环节 | 真实实现 | 关键文件与证据 |
|---|---|---|---|
| 1 | **解析** | MinerU **云端 API**：`POST /api/v4/file-urls/batch` 取上传地址 → PUT 上传（**必须显式带 Content-Length**，chunked 会被拒 `-10002`）→ 轮询 `GET /api/v4/extract-results/batch/{id}`（8s 间隔，超时 600s）→ 下载 zip → 清理中间产物 | `mineru/client.py`、`mineru/uploader.py`、`mineru/result.py`；配置 `config.py:17-27`（`base_url=https://mineru.net`、`model_pdf="pipeline"`、`model_html="MinerU-HTML"`、`language="ch"`、`batch_max=50`、`is_ocr=False`） |
| 2 | **清洗 + 切块** | **自研约 180 行**：去 `<sup>`/LaTeX/页眉页脚 → **标题扁平化修复**（MinerU 全输出 `##`，按 `^##\s+[一二三四五六七八九十]+、` 等正则恢复层级）→ 表格抽为 `[[TABLE_n]]` 占位符并独立成 HTML 块 → 按标题层级切块（`header_path` 继承）→ 超长章节按空行段落降级（阈值 `max_section_chars=1200`） | `chunking/pipeline.py`、`preprocess/clean.py`、`preprocess/headings.py`、`preprocess/tables.py`；31 个 pytest 锁定行为（`tests/`） |
| 3 | **页码锚定** | 从 `content_list.json` 建"文本片段 → `page_idx`"索引，前 20 字对齐（容忍 OCR 差异），找不到则 `page_idx=None` 不阻塞 | `anchors/page_anchor.py` |
| 4 | **内容复核 + 元数据标注** | **9 条正则**扫数字缺失（`为\s*次`、`最大剂量\s*[，。]`、`（\s*岁）`、`重复注射\s*次`、`需要\s*剂以上` 等）→ 命中即 `review=True`；再调 `pypdf` 提原 PDF 文字层做交叉校验给候选值；风险分级按关键词（`急救/肾上腺素/剂量` → caution，`休克/死亡/禁用` → emergency）；来源靠**手写映射表** | `validate/numbers.py`、`validate/pdf_layer.py`、`metadata/annotate.py`、`config.py:37-60`（正则）、`:63-89`（**20 条硬编码来源映射表**） |
| 5 | **入库 + 向量化** | pymysql 事务批量 `INSERT ... ON DUPLICATE KEY UPDATE`（幂等键 `kb_id = {doc_id}-{seq}`）；向量用 TokenHub OpenAI 兼容接口 `kinfra-text-embedding-0.6b`（1024 维）写回 `embedding` BLOB（float32 = 4096B），仅对 `status=1 AND embedding IS NULL` 且非 review 的条目生成（增量） | `store/knowledge_base.py`、`embed/hunyuan.py`、`embed/runner.py`；`config.py:100-121` |

### 2.2 数据与质量基线

| 项 | 现状 |
|---|---|
| 源语料 | 20 份（国内 7 + 国际 13），其中 **16 PDF + 4 HTML**（HTML 走 `MinerU-HTML` 引擎，需「HTML 无前缀标题推断」） |
| 入库条目 | **1586 条**（1530 section + 218 table） |
| review 条目 | 2 条（`[待复核]` 前缀，**不进检索**） |
| 向量 | 1584 条 × 1024 维 BLOB |
| 风险分级 | caution 26 / emergency 12 / low 1548 |
| 召回基线 | **精确 Recall@10 = 97.8%（44/45）**，已过 ≥90% 上线闸门 |
| 表结构 | `knowledge_base`（迁移 `017_knowledge_base.sql`，13 字段 + FULLTEXT ngram `(title, content, keywords)`） |

### 2.3 Agent 消费侧（唯一消费方）

| 项 | 现状 |
|---|---|
| 实现位置 | `minicare-agent/src/lib/tools/search-knowledge.js` —— **直接读同一张 MySQL 表** |
| 检索方式 | FULLTEXT ngram（`MATCH(title,content,keywords) AGAINST` 取 top20）+ **内存全表余弦**（进程级缓存 1584 行 × 4096B ≈ 6.5MB，10 分钟 TTL + stale-while-revalidate）取 top20 → **RRF 融合（k=60）** → top5 |
| 与入库的一致性 | 查询向量用 `minicare-agent/src/lib/embeddings.js`，**与离线入库同一模型同一维度**（`kinfra-text-embedding-0.6b` / 1024） |
| 降级链 | 无 `TOKENHUB_API_KEY` → 仅 FULLTEXT；query 向量化失败 → 仅 FULLTEXT；DB 不可用 → `{ found: false }` |
| 输出契约 | `{ found, items[{ id, kb_id, title, content, content_truncated, source, risk_level }], topK }`；单条 `content` 截断 800 字并打 `content_truncated` |
| 过滤语义 | `status=1` **且** `content NOT REGEXP '^\\[待复核\\]'` —— **靠正则反查内容前缀** |
| 服务端 | **`minicare-server` 无任何知识库模块或路由**（`src/` 下只有 agent/auth/family/baby/records/storage/voice 等，无 knowledge） |

### 2.4 现有 CLI 命令

```bash
kb-pipeline parse   --source <dir> --out <dir> [--force]   # 调 MinerU 云端，产物落目录
kb-pipeline chunk   --doc <doc_id> [--splitter self|llama] # 清洗→切块→锚定→校验→chunks.jsonl
kb-pipeline import  --chunks <jsonl> [--replace]           # chunks.jsonl → knowledge_base
kb-pipeline embed   [--limit N]                            # 全量 active 非 review → 向量写回
kb-pipeline pipeline --source <dir> --out <dir>            # 只串 parse → chunk（不含 import/embed）
```

## 3. 与旧 v3 设计的差异：为什么另起编号

`docs/prd/PRD-008/archive/` 下的 v3 PRD（PRD-KB-003 v3.2）与配套技术方案（DES-KB-004）**描述了另一个系统**。经代码核实，其前置假设有 6 处不成立：

| # | v3 的假设 | 核实结果 | 证据 |
|---|---|---|---|
| A1 | kb 后端是 **FastAPI**，检索基于 **llama-index**，向量库为 **Chroma** | **全部不存在**。真实为 click CLI + 自研切块 + pymysql + MySQL BLOB 向量 | `cli.py`、`chunking/pipeline.py`、`store/knowledge_base.py` |
| A2 | 语料是**医学论文**（DOI/PMID/Crossref/PubMed/研究类型） | 真实语料是**中文指南与共识 + 国际指南**，20 条映射里无一篇论文 | `config.py:65-89` |
| A3 | MinerU 2.5.x，后端名 `pipeline / vlm-transformers / vlm-sglang` | MinerU 已 **4.0.10**，后端名废弃，改为档位制 `flash/basic/standard/advanced` + `ocr_mode: auto\|txt\|ocr` | 调研快照 `MinerU/mineru/version.py:1`、`docs/next/tiers.md:15-20` |
| A4 | 存在"文档上传页""检索测试页"等已有实现 | 服务端与前端**均无知识库代码** | `minicare-server/src/`、`minicare-web/src/pages/` |
| A5 | 切块可改用 LlamaIndex NodeParser 家族 | 已实测否决：Recall 自研 64.4% vs LlamaIndex 31.1%，且 MinerU 单行 HTML 表格与 `ElementNodeParser` 不兼容 | `docs/CHUNKING-COMPARE-REPORT.md` |
| A6 | review 用 `risk_level=caution` + `content` 前缀表达，**不加列** | 该 hack 只支持二态，支撑不了本 PRD 需要的四态（待复核/已排除/已采纳/已恢复） | `store/knowledge_base.py:16`、`search-knowledge.js:27`；决策见 §19 D-06 |

**沿用下来的设计骨架**（这部分 v3 做得好，本文保留）：Step 化与产物寻址、`run_id` 含引擎版本与参数 hash、失效传播（下游标 `stale` 但产物不删）、~~两个人工暂停点的位置论证~~（暂停点已于 2026-10-09 移除，改为可选操作，见 02-能力设计 §6.5）、LLM 触点的成本意识、审查报告的分级方法论。

**另起编号的理由**：v3 的范围是「**单文档**的解析入库全流程」，其 §12 明确写「不在范围：知识库 CRUD、多用户与权限」。而本次要解决的**平台化**恰好就是那些被排除的部分（文档库与语料档案、切片生命周期、产物版本与发布回滚、检索质检闸门、Agent 消费契约）。范围不重叠 + 假设需重写 ⇒ 重写成本低于修订。

## 4. 技术债与已识别缺陷（本期必须收口）

| # | 缺陷 | 具体表现 | 影响 | 收口故事 |
|---|---|---|---|---|
| **T1** | `chunks.jsonl` 追加写入 | `store/knowledge_base.py:22` 用 `open(path, "a")`，`cli.py:88` 每次 `chunk` 都调它 | 重复跑持续膨胀；**无法分辨哪行是哪次跑的**，因此无法对比两次切块结果 | US-08 场景 5 |
| **T2** | 无产物版本 | 无 `run_id`、无 manifest、无参数指纹、无缓存 key | 改了参数只能整体重跑；出问题无法复现 | US-08 全篇 |
| **T3** | 关键词只从标题抽 | `metadata/annotate.py:14` 用 `re.findall(r"[\u4e00-\u9fff]{2,6}", chunk.title)`，最多 8 个 | FULLTEXT 是召回主力（评测确认它单独救回 6 题中的 5 题），但喂给它的词只来自标题 | US-09 场景 6 |
| **T4** | 质量闭环是断的 | `review=True` 只做两件事：`content` 加 `[待复核]` 前缀、候选值写本地 `var/review.md`（`cli.py:89-99`） | **无界面、无回填路径**，2 条 review 条目实质永久死数据 | US-06 全篇 |
| **T5** | 噪声块进检索 | 参考文献块、空表未被排除；`KB-MAPPING.md:12` 把 `NIAID_2010-食物过敏指南-115`（块标题 **References**）映射为 KB-A3 的 gold；`:25/:26/:43/:49` 把空表映射为 6 个条目的 gold | gold 污染 → 评测的"有害召回 16 条"是**伪指标**（报告 §3.2 已承认口径失真，但归因错了：根因是这两类块不该进检索，不是映射表粒度） | US-07 全篇、US-11 |
| **T6** | 来源映射硬编码 | `config.py:65-89` 手写 20 条 `文件名 → (来源名, 证据级别, 适用年龄)` | 新增语料必须改 Python 源码 | US-01、US-02 |
| **T7** | OCR 靠手工清单 | `config.py:27` 的 `ocr_files: list[str]` 需人工维护文件名；`is_ocr=False` 为全局默认 | 扫描件漏配即静默降质，无预检判定 | US-03（预检独立成步） |
| **T8** | 发布脚本硬编码 | `scripts/sync-kb-to-prod.py:24-26` 写死 `PROD_DB` / `DEV_DB`，按 `kb_id` 从 dev 拷 embedding 到生产 | 无快照、无回滚、无发布后验证；发错只能重跑脚本 | US-10 全篇 |
| **T9** | 评测游离在流程外 | `scripts/eval-recall-exact.py` 手动执行，与发布无关联；gold 映射由"每条目 top3 全取"自动生成 | 质量退化不会被拦住；映射表结构性地制造伪有害 | US-11 全篇 |
| **T10** | 无 Agent 契约 | `search-knowledge.js` 依赖 `knowledge_base` 的 7 个字段与固定响应结构，但无任何契约文档或校验 | 平台侧改字段会静默打挂智能体 | US-13 全篇 |
| **T11** | 无检索日志回流 | 线上未命中/低分召回没有记录，缺口只能靠人偶然发现 | 覆盖缺口不可见，语料补充靠猜 | US-12、US-13 |
| **T12** | **阈值配置文件根本不存在** | `config.py:11` 指向 `config/default.yaml`，`:138` 靠 `CONFIG_FILE.exists()` 才加载 —— 但 `minicare-platform/api/config/` 目录**不存在** → YAML 覆盖逻辑从未执行；`ARCHITECTURE.md` §12 声称的"阈值集中配置"是纸面声明，全部阈值实际写在 `config.py` 的代码默认值里（`:30-60` 切块与校验阈值） | §12.2「调参一处生效」这条 NFR 无法验收；调参会改代码而非改配置 | US-08、§12.2、§4.9 |
| **T13** | **llama-index 依赖声明与文档自相矛盾** | `pyproject.toml:9` 声明 `llama-index-core>=0.12`，且 `chunking/llama.py:14-15` 实际导入使用；但 `chunking/pipeline.py:3` 的 docstring 说"依赖 llama-index-core"，`ARCHITECTURE.md` §1.2 又说"切块不依赖" | 依赖体积与版本冲突面被低估；默认安装引入不必要的重依赖 | §4.2 |
| **T14** | **环境不可复现** | 无 `.venv`（未提交）、无 `.env.local`、无 `var/`（`.gitignore` 覆盖） | 现状是"在某台机器上能跑"，换机或重装无据可依 | §12.4 |
| **T15** | **超长章节降级对"单段落长文"失效** | `chunking/pipeline.py` 的 `_split_long` 只按**空行**（`\n\n`）分段聚合；若某章节是**一个没有空行的长段落**，`paras` 只有一项，循环不会切分 → 整段原样成为一块 | **实测（2026-10-03，严重过敏共识）**：把 `max_section_chars` 从 1200 降到 200，块数仍是 59 不变 —— 因为存在 **16,741 字符的巨型块**。而入库时 `embed/runner.py` 对文本**截断 2000 字符**再向量化，所以该块的向量只代表开头 2000 字，**向量召回被稀释**（FULLTEXT 仍覆盖全文） | §4.2 反面论证①、US-09 |

**技术债的收敛顺序**（与 §14 分期一致）：**T2/T1（产物与版本）是地基**，没有它 US-06/07/08 的"只重跑受影响步骤"无法成立；**T5/T4（质量门禁）是安全底线**，它直接决定家长看到的内容；**T6/T7（可维护性）是接入成本**；**T8/T9/T10/T11（发布与闭环）是本期价值的兑现点**；**T12/T13/T14（文档与代码不一致）在第 1 期一并收口** —— 这三项不阻塞平台化，但会让"阈值集中""环境可复现"两条 NFR 永远无法验收。

> T12/T13/T14 由 `TECH-015` §2.3 核实代码时发现（2026-10-03）；**T15 由第 1 期实现后的本地实测发现（2026-10-03）**，属 PRD v1.0 未记录项。
>
> ⚠️ **T15 的处置需要一次专门决策**：修它（引入定长兜底）会**改变切块结果**，从而使现有召回基线 97.8% 失效、必须重新评测。按 TECH-015 §4.2 的触发条件（单块 > 3000 字）**今天已满足**，但改动影响面覆盖整库 1586 条，因此**不在第 1 期擅自改动**。
