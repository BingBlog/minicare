## 18. 约束与风险

### 18.1 技术约束

| # | 约束 | 说明 |
|---|---|---|
| C1 | **单用户本机** | 无账号、无权限、无并发多用户；服务不对外监听 |
| C2 | **复用现有 Python 管线** | 不重写 `mineru/` `preprocess/` `chunking/` `validate/` `embed/`；只做接驳 |
| C3 | **不引入重型基建** | 不引入 Chroma / pgvector / ES / Redis / 对象存储 / Docker 编排；向量继续用 MySQL BLOB + 内存余弦 |
| C4 | **MinerU 走云端 API** | 不本地部署；受云端配额与网络影响 |
| C5 | **embedding 与检索必须同模型同维度** | 当前 `kinfra-text-embedding-0.6b` / 1024；换了需全量重嵌入 |
| C6 | **迁移编号** | 现最大 `020`，PRD-006 已占 `022`/`023`，本 PRD 用 `021` |
| C7 | **默认排除块不进索引** | 既无向量也无全文索引（保留数据），与 agent-poc 契约绑定 |

## 19. 决策记录（2026-10-02 逐条确认）

> 本表是本文档的**合宪审查依据**。改动任何一条，必须同步改本表并说明理由。

| # | 决策 | 结论 | 理由摘要 | 关联 |
|---|---|---|---|---|
| **D-01** | 阶段地图 | **4 阶段 + 1 贯穿线**：① 语料入库 ② 解析与切片 ③ 索引与发布 ④ 消费与验证；贯穿来源台账/质量门禁/产物版本与回滚/检索质检 | 四段正好对应"文件→块→线上数据→验证"的物理流转；贯穿线是横切所有阶段的治理能力 | §1.2 |
| **D-02** | 平台形态与使用范围 | **独立本地管理端，仅维护者一人使用**；**直接复用现有 `minicare-platform/api` Python 管线代码，不重写** | 管线是 Python 而前端是 React，内嵌会引入无谓的跨语言适配；单用户使账号与权限都不必要 | §5.1 |
| **D-03** | 知识库域范围 | **单库 + 表结构预留 `kb_domain`**（本期恒 `default`） | 当前只有敏宝医学一个库；预留字段使未来开新库（如职场文章）只需改配置，不必改表 | §7.1 |
| **D-04** | 存储与版本控制边界 | **平台自管 `data/` 目录**；源文件与产物**不进 git**（体积大）；台账**只存 DB 不进 git** | 源 PDF 与产物体积不适合进版本库；台账属运行数据而非配置，变更走迁移脚本即可追溯 | §5.3、R-01 |
| **D-05** | 语料类型 | **PDF + HTML 双轨** | 核实发现存量 20 份中有 4 份 HTML 指南（卫健委/广东/AAP/FDA）走 `MinerU-HTML` 引擎，若只做 PDF 会直接丢 4 份且召回基线需重测 | §5.2、R-05 |
| **D-06** | 检索状态存储 | **`knowledge_base` 加 `retrieval_status` + `review_state` 两个字段（迁移 021）** | 现有 `content` 前缀 `[待复核]` + `risk_level=caution` 的 hack 只支持二态，支撑不了「待复核/已排除/已采纳/已恢复」四态；检索端过滤也从正则反查变为普通 WHERE | §7.4、§13 H1 |
| **D-07** | 处理步骤划分 | **6 步**：预检 · 解析 · 正文清洗 · 切块 · 内容复核 · 索引 | 把「内容复核」从 chunk 里拆出独立成步，是"发现一条数字缺失 → 改规则 → 只重跑校验"成立的前提；沿用 4 步则每次都要重切 | §6.1 |
| **D-08** | 元数据必填项 | **年份 + 地区 + 证据级别**（其余缺失标 ⚠ 但不拦流程） | 这三项直接决定检索过滤与"国内共识 vs 国际指南"的冲突判定 | §7.1、US-04 |
| **D-09** | 重切后人工编辑 | **可找回 + 逐条确认**：按文本相似度在新切片中定位候选，列出可找回项由人确认是否迁移 | 改了切块参数就等于白校对，是校对成本的最大杀手；逐条确认避免模糊匹配误迁移 | US-05 |
| **D-10** | 关键词抽取与降级 | **LLM 生成**；LLM 不可用时**降级为「标题 + 正文规则抽取」并告警**；生成结果**落产物并按内容 hash 缓存** | 采纳 LLM 是选择质量优先；但必须有降级出口，否则索引步骤被外部服务卡死；缓存是成本的唯一有效约束 | US-09、R-03 |
| **D-11** | 缓存判据 | 步骤 ID + 上游产物内容 hash + 参数 hash + 引擎版本 + **平台代码版本** | 否则会出现"代码改了行为变了、缓存却仍命中"，这是最难排查的一类不一致。代价（任何代码改动使全部缓存失效）对单用户本机可接受 | §6.3 |
| **D-12** | 并发模型 | **解析步骤可并发**（云端 API，IO 密集）；**本地步骤串行**（CPU 密集） | 本机 CPU 有限；实测主要耗时在云端解析（约 1–2 分钟），本地切块仅 2–3 秒 | §5.4 |
| **D-13** | 失败策略 | **单份失败不中断整批**；失败项可**单步重试**；成功项不重跑 | 批量导入最怕"一份坏文件卡死整批" | US-03 |
| **D-14** | 解析进度呈现 | **阶段级 + 已耗时**（如「解析中 · 已等待 1m42s」），**不做百分比估算** | 云端只能轮询到任务状态，拿不到页级进度；"卡在 90% 的假进度条"比"没有进度条"更糟 | §5.4 |
| **D-15** | 噪声块默认动作 | **默认排除 + 可恢复，且人工决定优先于规则** | 医疗库宁可不召回也不召回错；但规则必有误判，必须留恢复出口且不让规则再次覆盖人工决定 | §7.5、US-07 |
| **D-16** | 回滚机制 | **发布快照**（发布前记录目标库现状，回滚 = 恢复快照） | 当前库仅 1586 条，快照成本可接受；增量反向应用逻辑复杂易漏，软回滚不彻底（改过的文档回不去） | §7.6、US-10 |
| **D-17** | 发布粒度 | **按文档增量发布** | 只写本次选定/改动的文档，其余保持；每次发布自动形成一个快照，可整体回滚。全量重发布慢且失败面大 | US-10 |
| **D-18** | 检索质检门槛 | **硬阻塞 + 可二次确认放行**（不达标默认拦下，但提供留痕的强制放行） | 既保证坏质量不静默流出，又不让一次指标波动把平台彻底锁死 | US-10、US-11 |
| **D-19** | gold 映射口径 | **人工精修主块（每条目 1–2 个）+ 语义判定**（命中块与题目主题语义相关也算命中） | 现有映射按"每条目 top3 全取"生成，一个块被 5 个条目引用就全算有害 —— `RECALL-REPORT.md` §3.2 承认的"16 条伪有害"根因在此 | US-11、R-09 |
| **D-20** | 检索契约载体 | **Markdown 契约文档 + 发布时自动校验** | 两个独立项目靠"记得同步"一定会漏；自动校验是这条链路上唯一的保险。共享 schema 代码包对当前规模过重 | §9、US-13 |
| **D-21** | 不做语言分档 | **不加语言列**，不做中英分档切块阈值 | 简化取舍，接受英文块按中文字符阈值切块；未来若英文检索效果明显偏差再单独立项 | R-02 |

### 20.3 已明确关闭的问题（避免重复讨论）

| 问题 | 结论 |
|---|---|
| 切块用自研还是 LlamaIndex？ | **自研**。已实测：纯向量 Recall 自研 64.4% vs LlamaIndex 31.1%；且 MinerU 单行 HTML 表格与 `ElementNodeParser` 不兼容（`CHUNKING-COMPARE-REPORT.md`） |
| embedding 用 0.6b 还是 4b？ | **0.6b**。已实测：0.6b 全面优于 4b（关键信息 13.0% vs 11.7%，Recall 86.7% vs 64.4%），且省 2.5 倍存储 |
| 检索用纯向量还是混合？ | **混合**。已实测：纯向量 86.7%，混合链路 97.8%，FULLTEXT 单独救回 6 题中的 5 题 |
| 是否走 PMC/JATS XML 优先路径？ | **不走**。语料全是指南与共识，20 条映射里无一篇论文 |
