## 0. 设计原则

**画像不是"数据的汇总"，而是"过敏管理阶段的判断"。**

罗列"喝奶 5 次、睡了 12 小时"没有价值——这些当日数据模型自己能查。画像要回答的是模型**查不出来、必须靠跨表推断**的三件事：

| 要回答的问题 | 为什么单靠工具查不到 |
|---|---|
| 宝宝现在处于 CMPA 管理的哪一步？ | 需要把"配方阶梯 + 排敏状态 + 症状活跃度 + 生长趋势"四个信号合起来判断 |
| 有什么**矛盾或风险**正在发生？ | 需要跨表对照（如"已标记过敏的食材还在吃"） |
| 当前哪些结论**不可信**？ | 需要知道数据新鲜度与覆盖率（如"大便性状 78% 未填"） |

因此本文的信号体系分三层：

```
第 1 层  事实信号  ——  可靠可算的客观值（配方、分位数、清单）
第 2 层  推断信号  ——  由事实派生的状态判断（转奶阶段、排敏合规性、生长趋势）
第 3 层  元信号    ——  对信号本身的可信度标注（新鲜度、覆盖率、矛盾标记）
```

> 第 3 层是此前方案完全缺失的部分，也是最能提升助手"活人感"的地方——它让助手知道**什么时候该说、什么时候该问、什么时候不该下结论**。

### B. ★配方与转奶进度（用户点名）

这是本次最有价值的发现：**转奶进度是可算的，而且库里一直有数据**。

`feeding_formula_mix` 记录了每一顿奶的**奶粉类型 + 勺数**，支持混合配比：

```
milk_type 枚举：aa=氨基酸 | eh_no_lactose=深度水解无乳糖 | eh_lactose=深度水解含乳糖 | ph=适度水解 | std=普通奶粉
scoops    DECIMAL(4,2)   ← 支持 0.25/0.33 等分数勺
```

**CMPA 配方阶梯**（从高到低）：`aa` > `eh_no_lactose` ≈ `eh_lactose` > `ph` > `std`
向上 = 升级（症状加重）｜向下 = 降级（耐受改善）

#### 信号定义

| 信号 | 算法 |
|---|---|
| `formula.current` | 近 7 天各 `milk_type` 的勺数占比（如 `{eh_lactose: 0.75, ph: 0.25}`） |
| `formula.ladder` | 主导类型对应的阶梯位（`amino_acid`/`extensively_hydrolyzed`/`partially_hydrolyzed`/`standard`） |
| `formula.status` | `stable`（单一类型且 14 天未变）/ `transitioning`（多类型混合，构成在变）/ `stalled`（混合构成 ≥14 天完全不变）/ `switched`（近 30 天整体阶梯变化） |
| `formula.direction` | `escalated`（阶梯上移）/ `deescalated`（下移）/ `same` |
| ★`formula.stalledDays` | 当前构成保持不变的天数 |
| `formula.lactose` | 含乳糖 / 无乳糖（`eh_lactose` vs `eh_no_lactose`）——**乳糖耐受信号** |
| `formula.lastChangedAt` | 最近一次类型构成发生变化的日期 |

#### 实测（生产旺仔，真实用户）

```
2026-07-20 ~ 08-15   eh_lactose 为主 + aa 间歇 3~12 勺/天   → 混合期（氨基酸递减）
2026-08-16 起        aa 完全消失，纯 eh_lactose              → 稳定期
2026-09-19（今天）   纯 eh_lactose 28 勺                    → 已稳定 34 天
```

⇒ 画像输出：**"已停用氨基酸 34 天，当前为纯深度水解（含乳糖）配方，处于稳定期。"**

#### 实测（dev 旺仔，另一个对照）

```
2026-08-17 ~ 09-03   深度水解 12 勺 + 适度水解 4 勺 = 恒定 25% 适度水解，持续 18 天未变
2026-08-18 / 08-29   出现「轻微皮疹 / mild」过敏反应
```

⇒ 画像输出 + **矛盾标记**：**"适度水解占比 25% 已停滞 18 天，期间出现 2 次皮疹——转奶停滞可能与轻度反应有关，建议与医生确认是否继续。"**

> 这一条正是第 3 层"矛盾检测"的价值：单看配方是"稳定"，单看症状是"偶发皮疹"，**只有合起来才发现关联**。

#### SQL（1 条）

```sql
SELECT DATE(r.record_time) AS d, m.milk_type, ROUND(SUM(m.scoops),2) AS scoops
FROM feeding_formula_record r
JOIN feeding_formula_mix m ON m.record_id = r.id
WHERE r.baby_id = ? AND r.record_time >= DATE_SUB(CURDATE(), INTERVAL 60 DAY)
GROUP BY d, m.milk_type ORDER BY d
```
（在服务端按天聚合出构成序列，再算 status / stalledDays）

#### ★排敏合规性检查（新增，敏宝安全底线）

引敏宝排敏的核心规则是**"一次只引入一种新食物，观察 3-7 天，期间不引入其他新食物"**。画像应主动检测违规：

| 检查项 | 规则 | 实测结果 |
|---|---|---|
| `multiObserving` | 观察窗口是否重叠 | 牛肉(09-14~09-17) → 小米粉(09-18~) **合规串行** ✓ |
| ★`staleObserving` | observing 任务超期未结 | **火龙果 day2/3 停在 09-05，已停滞 14 天** ⚠ |
| ★`eatingMarked` | 已标记 suspected/allergic 的食材是否仍在食用 | 需与 `feeding_food_item` 对照（生产芹菜待核）⚠ |
| ★`nameDuplication` | 同一食材因命名不一致重复建档 | **西兰花/西兰花泥、鸡肉/鸡肉泥、纯米粉/小米粉、米粉+南瓜泥** 4 组重复 ⚠ |

> `nameDuplication` 直接影响"已排敏食材数"的准确性（实际 12 种可能只对应 9 种真实食材），也让 `food_observation.food_name` ↔ `feeding_food_item.food_name` 的软关联断裂。**建议在画像层做归一化映射表**（去掉"泥/粉/粥"等形态后缀）。

### J. ★矛盾与风险检测（最有价值的层）

画像输出 `flags[]`，让模型主动提示而非被动应答：

| # | 检测项 | 触发条件 | 实测 |
|---|---|---|---|
| 1 | **过敏食材仍在食用** | `food_observation.status ∈ (suspected, allergic)` 的食材出现在近 14 天 `feeding_food_item` | 生产芹菜待核 ⚠ |
| 2 | **排敏任务停滞** | `observing` 且 `updated_at` 距今 > `observation_days` | 生产火龙果停滞 14 天 ⚠ |
| 3 | **多个排敏任务窗口重叠** | 两个 `observing` 的观察期有交集 | 生产合规 ✓ |
| 4 | **转奶停滞** | `formula.status = stalled`（混合构成 ≥14 天不变） | dev 25% 混合停滞 18 天 ⚠ |
| 5 | **转奶期出现过敏反应** | 4 触发 + 同期 `health_record` 有过敏事件 | dev 停滞期 2 次皮疹 ⚠⚠ |
| 6 | **配方阶梯上移** | 近 30 天 `direction = escalated` | 生产 06-04 上氨基酸 ⚠ |
| 7 | **生长分位下降** | `trend = falling` 或连续 2 次降档 | 待算 |
| 8 | **关键数据陈旧** | 症状/生长 staleDays 超阈值 | 生产症状 31 天 ⚠ |

> 这些 flag 应当**由服务端算好直接给模型**，而不是让模型自己拼 SQL 推断——既省 token 又保证一致性（同"排敏进度"从模型数 205 条改为服务端聚合的思路一致）。

## 3. 注入 prompt 的最终形态

在 `prompts/system.js` 的 `ctxBlock` 后追加（示意，以生产旺仔为例）：

```
【宝宝画像】旺仔，8 个月 22 天，男，轻度牛奶蛋白过敏（过敏原：牛奶）。
配方：已停用氨基酸 34 天，当前为纯深度水解（含乳糖）配方，稳定期。
喂养：已完全停止母乳，纯配方奶 + 辅食，已尝试食材 12 种。
排敏：已耐受 12 种；疑似 2 种（芹菜/生菜，均轻度）；观察中 小米粉（第 1/3 天）。
生长：体重 8.45kg（P50-P85）、身长 70.5cm（P50-P85）、头围 44.5cm（P50-P85），趋势平稳。
医疗：已接种 4 针，儿保 1 次，就诊 1 次；最近记录 9 月 6 日。
```

## 4. 需新增的字段（migration 022 建议）

| 字段 | 表 | 用途 | 优先级 |
|---|---|---|---|
| `allergy_diagnosed` | `baby_profile` | 区分"家长自述"与"医院确诊"，决定回答口径 | P0 |
| `family_atopy_history` JSON | `baby_profile` | 家族过敏史（最强遗传风险信号） | P1 |
| `allergy_diagnosed_at` DATE | `baby_profile` | 确诊时间 → 算"已管理时长" | P2 |
| `mother_elimination_diet` JSON | `baby_profile` | 母乳期母亲忌口清单（若混合喂养） | P2 |

> 前两个字段虽小，但决定画像的**断言强度**。`allergy_level` 线上大量为 `unknown`，也说明现有字段填写引导不足。

## 5. 实施顺序与成本

| 阶段 | 内容 | SQL 数 | 说明 |
|---|---|---|---|
| 1（P0） | A 基本 + B 转奶 + C 喂养 + I 新鲜度 | 3 | 纯查表聚合，改动最小 |
| 2（P0） | D 排敏（双源合并 + 合规检查） | 2 | 含归一化映射表（服务端常量） |
| 3（P0） | E 生长分位数（复用 `growth.js`） | 1 | 零新增依赖 |
| 4（P0） | J 矛盾检测（依赖 1-3 结果，纯内存计算） | 0 | 建议作为 `profile.js` 的最后一步 |
| 5（P1） | F 症状 + G 医疗 | 1 | G 组需 `hasTypedMedical` 运行时探测降级 |
| 6（P1） | migration 022（画像补字段） | — | 需先在 staging 演练 |

**总成本**：约 **7 条 SQL**，单宝宝数据量下每条 <50ms；配合原方案的 **5 分钟 TTL 缓存**，对 4.3-6.8s 时延影响可忽略。

**失败降级**：任一组信号查询失败 → 该组置空并标注 `degraded`，**其余组照常注入，画像缺失不影响对话**。
