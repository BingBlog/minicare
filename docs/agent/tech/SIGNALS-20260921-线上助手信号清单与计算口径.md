# 线上助手信号清单与计算口径

> **文档编号**：SIGNALS-20260921
> **适用版本**：`minicare-agent-015`（线上 production，2026-09-21 上线）
> **核实方式**：逐行读 `agent-poc/src/lib/{profile,perception,query,growth}.js` 与 `src/lib/tools/*.js`，非依据设计文档转述
> **一句话**：助手回答里出现的每一个数字，都能在下文找到它的来源表、SQL 口径、派生规则和阈值出处。
> **不在本文范围**：知识库检索（search_knowledge）、图片理解（视觉模型）、日记生成（generate_diary）—— 那三条是"内容"链路，不是"信号"链路。

---

## 1. 总览：信号分四层

助手拿到一个数字，路径不是"模型去查库"，而是**服务端先算好结论、注入 prompt，模型只负责组织语言**。因此信号按"离原始数据多远"分成四层：

```
第 0 层  上下文与日期        2 个   → 每轮必注入（无 SQL）
第 1 层  原始数据维度        9 维   → 模型按需调用 query_baby_data 自查明细
第 2 层  画像信号        5 组 41+  → 每轮注入，答"是什么样"
第 3 层  现状感知信号    6 板块 60+ → 每轮注入，答"走到哪了、这样走合理吗"
第 4 层  分析派生信号     3 scope  → 模型按需调用 analyze_baby_data，答"趋势/总结/生长水平"
```

两层注入（第 2、3 层）合计约 833 字符/轮，是**每轮固定成本**（≈300 token）。

关键区别：

| 层 | 谁在算 | 何时算 | 模型能看到什么 |
| --- | --- | --- | --- |
| 第 0 层 | 服务端 | 每轮 | 今天/昨天的具体日期 |
| 第 1 层 | 服务端 | 模型主动调用时 | 原始记录明细与 SQL 聚合值 |
| 第 2 层 | 服务端 | 每轮（5 分钟缓存） | 已算好的中文结论 |
| 第 3 层 | 服务端 | 每轮（5 分钟缓存） | 已算好的中文结论 + 判定 |
| 第 4 层 | 服务端 | 模型主动调用时 | 趋势方向、异常点、百分位档 |

## 3. 第 0 层：上下文与日期信号

| # | 信号 | 值 | 计算口径 | 代码位置 |
| --- | --- | --- | --- | --- |
| 0-1 | 今天 | `YYYY-MM-DD` | `cstToday()` = `Date.now() + 8h` 后取 ISO 串前 10 位。**不用 `toISOString()`** —— UTC 在 00:00-08:00 会差一天 | `profile.js::cstToday` |
| 0-2 | 昨天 | `YYYY-MM-DD` | 今天 - 1 天，纯日期算术（`shiftDays(today, -1)`），与本地时区无关 | `system.js::shiftDays` |

注入形态：

```
【当前日期】今天 2026-09-21，昨天 2026-09-20（北京时间）。
【当前上下文】familyId=... babyId=...（宝宝档案可在数据接入后查询）
```

**为什么必须有**：模型没有内置时钟。缺这一条，"帮我写日记"会按训练数据的年份猜日期；这也是 F2 修复的根因。

## 4. 第 1 层：原始数据维度（模型自查通道）

模型调用 `query_baby_data(metric, days, aggregate)` 时走的就是这一层。`days` 服务端 clamp 到 **1-90**。

### 4.1 维度 → 数据表映射

| metric | 中文 | 数据表 | 时间列 | 数值列 | 过滤条件 |
| --- | --- | --- | --- | --- | --- |
| feeding | 喂养 | 4 张子表（见 §4.2） | record_time | 分表 | 无 |
| sleep | 睡眠 | sleep_record | start_time | duration_min | `status='ended'` |
| diaper | 尿布 | diaper_record | record_time | — | 无 |
| growth | 生长 | growth_record | record_date | weight_g | 无 |
| health | 健康 | health_record | record_time | temperature | 无 |
| symptom | 表现 | symptom_record | record_time | — | 无 |
| activity | 活动 | activity_record | record_time | duration_min | 无 |
| medical | 就医 | medical_record | visit_date | — | 无 |
| medication | 服药 | medication_record | record_time | — | `deleted_at IS NULL` |

总计覆盖 **13 张表**（feeding 计 5 张，见下）。

### 4.2 feeding 的四个子表

| 子表 key | 中文 | 表 | 输出字段 |
| --- | --- | --- | --- |
| breast | 母乳 | feeding_breast_record | side（侧别）、duration_min |
| formula | 配方奶 | feeding_formula_record | duration_min、ml（formula_ml） |
| food | 辅食 | feeding_food_record LEFT JOIN feeding_food_item | food_name、amount_g、amount_note |
| supplement | 营养素 | feeding_supplement_record | supplement_items（JSON 解析为 label/key/dose/unit） |

**口径要点**：`food` 子表因 LEFT JOIN 每个食材膨胀一行。取明细时非 food 子表预取 `limit` 行、food 子表预取 `limit*3` 行，合并排序后再 `slice(0, limit)`。此前非 food 子表仅预取 `ceil(limit/4)`，当日顿数一多就把配方奶行截断 → 模型按可见明细心算总量出错（生产日记 460 vs 880 事故根因）。

### 4.3 五种聚合方式

| aggregate | 返回 | 口径 |
| --- | --- | --- |
| list | `rows`（最多 10 条明细） | 按时间倒序取最近 10 条。**不得用于加总推断总量** |
| count | `summary.count` | 窗口内记录条数 |
| sum | `summary` | 数值列直接 SUM；喂奶给出 `breast_min` 与 `formula_ml` 两项 |
| avg | `summary` | 数值列 AVG。temperature 保留 1 位小数，其余取整 |
| trend | `rows`（按天） | 按 `DATE(时间列)` 分组，每天给 `count` + `total` + `avg` |

### 4.4 跨环境兼容：medical 的列探测

`medical_record` 在 dev/staging 是 34 列（已上 migration 020），生产库停在 019 只有 18 列。处置：

- **基础列**（15 列，两库都有）：`id / baby_id / visit_date / visit_time / visit_type / hospital / doctor / diagnosis / result_summary / note / follow_up_date / follow_up_time / medications / photo_ids / created_at`
- **类型化列**（16 列，仅 020）：`vaccine_*`(7) / `checkup_*`(7) / `sick_*`(2)
- 探测方式：`information_schema` 查 `medical_record.checkup_weight_g` 是否存在，结果缓存；生产库自动退化为基础列。**探测列不能用 `visit_type`** —— 后者生产库早已存在，探不出来。

### 4.5 隐私列剔除

`medication` 维度**不使用 `SELECT *`**，而是固定列清单 `medication_name, dose, record_time, note`。原因：表里有 `recorded_by`（user_account UUID）与 `deleted_at`，`SELECT *` 会把内部标识一并塞进模型上下文。

全局仅 `medical`（跨环境 schema 差异）与 `medication`（隐私列剔除）两个维度使用显式列，其余保留 `*` 以免列清单失维护。

## 5. 第 2 层：画像信号（`lib/profile.js`）

定位：答"**是什么样**"。5 组只读 SQL + 5 分钟进程内缓存 + 单组失败静默降级。

### 5.1 A 组 基本情况（`queryBasic`）

| 信号 | 口径 |
| --- | --- |
| name | `baby_profile.name`，`deleted_at IS NULL` |
| gender | `male` / `female` / `unknown` |
| birthDate | 收敛为 `YYYY-MM-DD` |
| ageText | **月龄「X 个月 Y 天」精确表述**：先算整月数，再从"出生日 + 整月数"到今天的实际天数 |
| allergyTypes | JSON 列，13 种枚举（milk/egg/wheat/soy/peanut/nut/fish/shrimp/crab/rice/corn/oat/beef） |
| allergyLevel | mild / moderate / severe → 轻度/中度/重度 |
| birthWeightG | 出生体重（克） |

### 5.2 B 组 配方与转奶进度（`queryFormula`）—— 核心信号

**数据源**：`feeding_formula_record` JOIN `feeding_formula_mix`，窗口 **近 60 天**，按「日 × 奶型」聚合勺数。

CMPA 配方阶梯（`LADDER_LEVEL`，高→低；向上=升级，向下=降级）：

| 奶型 key | 中文 | 阶梯位 | 乳糖 |
| --- | --- | --- | --- |
| aa | 氨基酸配方 | 4 | 无乳糖 |
| eh_no_lactose | 深度水解（无乳糖） | 3 | 无乳糖 |
| eh_lactose | 深度水解（含乳糖） | 3 | 含乳糖 |
| ph | 适度水解 | 2 | — |
| std | 普通配方 | 1 | — |

**阶梯推进路径**（`NEXT_STAGE`）：`aa → eh_lactose`、`eh_no_lactose → ph`、`eh_lactose → ph`、`ph → std`。两种 eh 同阶，故都指向 `ph`。

计算口径逐项：

| 信号 | 计算口径 |
| --- | --- |
| current | **构成占比（勺数口径），取近 7 天**，降序 `[[type, ratio], ...]` |
| dominant | current 第一位（占比最高者） |
| ladderLevel | `LADDER_LEVEL[dominant]`，即 1-4 |
| status | 单一奶型 → `stable`；混合且停滞 <14 天 → `transitioning`；混合且停滞 ≥14 天 → `stalled` |
| stalledDays | **构成停滞天数**：从今天往前找「连续同一构成签名」的最早一天，算它到今天的间隔 |
| stableSince | 上述连续段的最早日期 |
| stalledAtLeast | 连续段起点 == 窗口最早一天（说明真实天数可能更长，只能说「至少」） |
| direction | 近 30 天「首日主导类型阶梯位」与「当日主导类型阶梯位」对比 → `escalated` / `deescalated` / `same` |
| lactose | 仅 `eh_lactose` → 含乳糖；`eh_no_lactose` 或 `aa` → 无乳糖；其余 null |
| aaLastAt | 最后一条含 `aa` 的日期 |
| aaStoppedDays | 最后含 aa 日期距今，**且近 7 天构成中 aa 占比为 0**（即确已停用） |
| lastRecordAt | 窗口内最后一条配方记录日期 |
| staleDays | 今天 - lastRecordAt |
| basisLabel | 近 7 天有记录 → `近 7 天`；否则 `截至 {退回日}` |

**两个必须知道的口径细节**：

1. **构成签名用「占比」不用「绝对勺数」**。签名 = 各奶型整数百分比排序后以竖线拼接（如「深度水解 75 / 适度水解 25」）。用绝对勺数会把「构成没变」误判成「天天在变」（今天 24 勺、明天 28 勺），停滞天数永远归零。
2. **配方空档兜底**：近 7 天一条记录都没有时，退回「最近 7 个**有记录**的日子」算构成，并在 `basisLabel` / 渲染文本里标注截至日期 —— 配方类型是最稳定的信号，不该因短期空档整段消失，但也绝不能把旧构成当当前状态。

### 5.3 C 组 喂养方式（`queryFeeding`）

| 信号 | 计算口径 |
| --- | --- |
| mode | 见下方判定规则 |
| sinceBreastDays | 今天 - 最后一次母乳记录日期 |
| lastBreastAt | 最后一次母乳记录日期 |
| breastCount30 | 近 30 天母乳记录条数（**仅作展示参考，不参与判定**） |
| formulaRecords14 | 近 14 天配方奶记录条数 |
| avgFormulaMl7 | 近 7 天**配方奶日均毫升**：先把每顿 SUM 成当日总量，再对「有记录的天」取 AVG |
| solidKinds30 | 近 30 天辅食涉及的不同食材名数（`COUNT(DISTINCT food_name)`，**未归一化**） |
| supplementDays30 | 近 30 天有营养素记录的天数 |

**喂养方式判定（硬规则）**：按「最近一次母乳距今」判，阈值 `WEANED_DAYS = 14` 天。

| 条件 | mode |
| --- | --- |
| 从无母乳记录，或最近一次母乳距今 ≥ 14 天 | `formula_only`（已停母乳，**有效结论**） |
| 距今 < 14 天 且 近 14 天有配方奶记录 | `mixed` |
| 距今 < 14 天 且 近 14 天无配方奶记录 | `breast_only` |
| 其余 | `unknown`（不下结论） |

**禁止用「30 天累计条数 > 0」判仍在母乳** —— 那是滞后指标：09-03 停母乳的宝宝到 09-19 仍有 5 条落在 30 天窗口内，按条数会误判成混合喂养。已停时渲染层必须显式标注「30 天窗口内尚有 N 条旧记录，属历史数据，不代表仍在母乳」。

### 5.4 E 组 生长分位（`queryGrowth`）

取 `growth_record` **最近 2 条**，按性别 + **测量当天月龄**算百分位。

| 信号 | 口径 |
| --- | --- |
| latest.weightKg | `weight_g / 1000` |
| latest.heightCm | `height_mm / 10` |
| latest.weightP / heightP | `percentileOf(月龄, 性别, 类型, 值).p` |
| latest.months | 测量当天的整月龄（`ageInMonths(birthDate, record_date)`） |
| previous | 上一条测量，同口径 |
| staleDays | 今天 - 最近测量日期 |

### 5.5 I 组 数据新鲜度（`queryFreshness`）—— 元信号

一条 8 路 UNION ALL 的 SQL，每路取 `MAX(时间列)`：

| 源 key | 中文 | 表 / 时间列 | 陈旧阈值（天） |
| --- | --- | --- | --- |
| formula | 配方奶 | feeding_formula_record.record_time | 3 |
| food | 辅食 | feeding_food_record.record_time | 3 |
| supplement | 营养补充 | feeding_supplement_record.record_time | 3 |
| medication | 服药 | medication_record.record_time（过滤 deleted_at） | 3 |
| growth | 生长测量 | growth_record.record_date | 45 |
| symptom | 症状 | symptom_record.record_time | 14 |
| medical | 就医记录 | medical_record.visit_date | 45 |
| diary | 日记 | baby_diary.diary_date | 3 |

每源输出 `{ lastAt, staleDays }`。渲染规则：`无记录` / `今天` / `昨天` / `N天前（较旧）`（超过阈值才加「较旧」）。

**渲染顺序**（`renderProfileBlock` 硬编码）：formula → food → supplement → medication → growth → symptom → medical。日记不渲染（只存在于数据结构里）。

### 5.6 画像渲染块形态

```
旺仔，8 个月 24 天，男。轻度牛奶蛋白过敏（过敏原：牛奶）。
配方：当前为纯深度水解（含乳糖）配方；乳糖类型：含乳糖；已停用氨基酸配方 36 天；构成稳定至少 30 天。
喂养：已停止母乳（最后一次母乳记录在 17 天前，30 天窗口内尚有 5 条旧记录，属历史数据，不代表仍在母乳）；近 7 天配方奶日均约 620 毫升；近 30 天辅食涉及 22 种食材。
生长：体重 9.2 千克（P50-P85）、身长 71 厘米（P50-P85），趋势平稳（测量于 2026-09-10，7 月龄）。
数据新鲜度：配方奶今天 / 辅食今天 / 营养补充3天前 / 服药今天 / 生长测量11天前 / 症状32天前（较旧） / 就医记录无记录。
【画像使用要求】
- 以上是服务端算好的结论，直接作为前提使用，不要向家长复述"你的记录显示…"这类统计口径话术；
- 喂养方式以本画像为准：标注"已停止母乳"时，回答与日记中都不要出现"母乳喂养/混合喂养/亲喂"等默认表述；
- 所有辅食与喂养建议默认带牛奶蛋白过敏前提；
- 标注"较旧"或"无记录"的信号不要当作阴性结论，也不要提醒家长补记录。
```

## 6. 第 3 层：现状感知信号（`lib/perception.js`）

定位：答"**走到哪了、这样走合理吗**"；**不回答**"要去哪"。三个只读查询 + 复用画像，5 分钟缓存。

**四条设计约束**（决定了它能做什么、不能做什么）：

1. **单一真相源** —— 阶段 / 月龄 / 新鲜度一律复用 `profile.js`，参考值只在 `REF` 定义一次。
2. **失败静默降级** —— 任一组查询失败 → 该组置空，其余照常注入。
3. **只出事实与判定，不出建议** —— 建议由对话产生。
4. **不设目标** —— 行业对"每阶/总时长"无共识（见 `RESEARCH-20260920`），故只算"到哪了 + 合理吗"，不做倒计时、不做待办。

### 6.1 板块① 转奶阶段与进度（复用 `profile.formula` + 派生）

| 信号 | 口径 |
| --- | --- |
| key / label | 主导奶型及其中文名 |
| level | 阶梯位 1-4 |
| nextKey / nextLabel / nextLevel | `NEXT_STAGE[dominant]` 及其阶梯位 |
| gapToEnd | `level - 1`（还差几阶到普通配方） |
| mix | 近 7 天构成占比 |
| nextPct | 下一阶在当前构成中的占比（0-1）。**纯阶时期恒为 0** |
| stableDays | = `formula.stalledDays`（本阶构成稳定天数） |
| stableAtLeast | = `formula.stalledAtLeast` |
| status / lactose / aaStoppedDays | 同画像口径 |
| staleDays / lastRecordAt | 同画像口径 |
| verdict | 四档判定，见下 |

**verdict 判定（`stage` 派生）**：

| 条件 | 结论 |
| --- | --- |
| `level === 1` | 已在普通配方（终点） |
| `stalledDays < 7` | 未满下限，观察中 |
| `stalledDays < 14` | 进度正常 |
| `stalledDays >= 14` | 本阶已 N 天 ≥ 参考 14 天，具备推进条件（需无症状前提） |

> **反直觉点（必须配对展示）**：纯阶时期下一阶占比恒为 0%，因此"阶内进度 0%"是**正常状态**，不是"没进展"。渲染时它必须与"本阶已 N 天 / 参考 14 天"配对出现，否则家长会误读成停滞。

**`stage` 可以为 `null`**（尚无配方记录的宝宝：新用户 / 纯母乳 / 未开始转奶）。这是**合法状态不是异常** —— `buildFlags()` 里曾有漏守卫导致整个感知层降级的 bug（见 §6.7）。

### 6.2 板块② 排敏进度（`queryObservations`）

**数据源**：`food_observation` **全量**（量级几十条），按 `updated_at DESC`。

排敏五态（`OBS_STATUS`，全产品统一口径）：

| key | 中文 |
| --- | --- |
| observing | 观察中 |
| safe | 已耐受 |
| suspected | 疑似 |
| allergic | 已确认过敏 |
| paused | 已暂停 |

| 信号 | 口径 |
| --- | --- |
| total | 建档总条数 |
| byStatus | 五态各自条数（**五态之和恒等于 total**） |
| safeCount | `status='safe'` 的**条数** |
| safeKinds | 已耐受**归一化去重后的食材种数**（西兰花与西兰花泥算 1 种） |
| safeNames | 归一化后的食材名数组 |
| dupGroups | 同一归一化名对应多个原始名 → 重复建档组 `{ normalized, raw[] }` |
| observing[] | 每项含 `name / day（current_day）/ days（observation_days，缺省 3）/ idle / stalled` |
| stalledObserving | `observing` 中 `idle > days` 的项（排敏任务停滞） |
| suspected[] | `{ name, severity }` |
| allergic[] | 已确认过敏的食材名 |
| paused[] | 已暂停的食材名 |

**停滞判定口径**：`idle` = 今天 − DATE(updated_at)（该条目最后一次被推进距今），`days` 取 observation_days，缺失时缺省为 3；`stalled` 为 idle 大于 days。

> 注意 `idle` 的锚点是 `updated_at` 而不是 `first_intro_at` —— 它衡量的是"这条排敏记录多久没被推进了"。

### 6.3 食材归一化与七大类归类（贯穿板块②③④）

**归一化三步**（`normalizeFoods`）：

1. **复合名拆分** —— 按 `+ ＋ 、 ， ,` 切分（`纯米粉+南瓜泥` → 双项）
2. **剥修饰** —— 前缀（纯/熟/自制/新鲜/有机/进口）与后缀（米糊/泥糊/泥/糊/粥/水/汁/条/块/片/粉/沫/羹/汤）循环剥离，且保留长度保护（剥后至少剩 2 字）
3. **别名兜底** —— `ALIAS` 表查询，**当前刻意留空**

### 6.5 板块④ 已耐受维持暴露（`queryEaten` + 交叉）

## 7. 第 4 层：分析派生信号（`analyze_baby_data`）

三个 scope，模型主动调用。

### 7.1 scope=trend 单维趋势

| 信号 | 口径 |
| --- | --- |
| trend | `up` / `down` / `flat`，见下 |
| trendReason | 中文说明（如「末期均值约为初期 1.4 倍」） |
| keyNumbers | 最后一天的日期与条数 |
| anomalies[] | 见下 |
| rows[] | 底层按天数据 |

**趋势判定（`judgeTrend`）**：

- 数据点 < 4 天 → `flat`，理由「数据点不足」
- 取**首 3 天均值**与**末 3 天均值**，算 `ratio = lastAvg / max(firstAvg, 1)`
- `ratio > 1.3` → `up`；`ratio < 0.7` → `down`；否则 `flat`
- 首末均值都为 0 → `flat`，理由「无数值数据」

**异常点判定（`findAnomalies`）**：对每一天，取**前后各 2 天**（窗口内可得部分）的均值作对照，若「当日值与均值之差的绝对值」超过均值的 50% 则记为异常，提示「当日数值与前后 2 天均值偏差超过 50%，请确认是否误录」。

### 7.2 scope=summary 跨维综合总结

默认遍历**全部 9 维**（可用 `metrics` 参数收窄）。

| 输出 | 口径 |
| --- | --- |
| dimensions[] | 每维 `{ metric, label, hasData, summary?, days, count }` |
| daily[] | 逐日合并明细，**只写 > 0 的字段** |
| weeks[] | 窗口 > 14 天时按约 7 天一段聚合 |
| anomalies[] | 逐维异常点汇总 |
| note | 数据来自最近 N 天共 X 条 |

**daily 字段映射**（`digestPatch`）：

| metric | daily 字段 | 单位 |
| --- | --- | --- |
| feeding | formula_ml / breast_min / food_count | 毫升 / 分钟 / 次数 |
| sleep | sleep_min | 分钟 |
| activity | activity_min | 分钟 |
| diaper | diaper_count | 次数 |
| symptom | symptom_count | 次数 |
| growth | growth_count | 次数 |
| health | health_count | 次数 |
| medical | medical_count | 次数 |
| medication | medication_count | 次数 |

维度取值规则：`count > 0` 时取 trend 铺进 daily；`count > 0` **且不是 growth/symptom/medication** 时额外取 sum 填 `brief.summary`（这三个维度无数值列可加总）。

**weeks 段内字段**：formula_ml / breast_min / sleep_min / activity_min / food_count / diaper_count / symptom_count / growth_count / health_count / medication_count / record_days / feed_days / sleep_days / activity_days。分段锚点用 **DB 的 `CURDATE()`**，与查询时间窗同一时区，避免本地/DB 差一天。

### 7.3 scope=growth 生长曲线解读

| 信号 | 口径 |
| --- | --- |
| months | **最后一次测量当天**的月龄（历史测量不能用当前月龄，否则百分位偏移） |
| weight.lastKg / measuredAt / deltaKg / p / percentile | deltaKg = 窗口内最后一次 − 第一次 |
| height.lastCm / measuredAt / deltaCm / p / percentile | deltaCm 同上 |
| sex / ref | 性别与中国 2023 儿科生长参考 |

**百分位档（`growth.js::bucket`）**：参考表 0-36 月、19 个锚点（0/1/…/12/15/18/21/24/30/36），月龄落在锚点之间时**线性插值**。

| 条件 | 输出 |
| --- | --- |
| 值 < P3 参考值 | 低于P3 |
| 值 ≥ P97 参考值 | 高于P97 |
| 落在 P3-P15 之间 | P3-P15 |
| 落在 P15-P50 之间 | P15-P50 |

> ⚠️ **`bucket()` 的 NaN 守卫必须保留**。非有限输入（月龄 NaN / 插值越界）下，区间比较会全部为 false，静默落到函数末尾 `return`，**凭空造出「P85-P97」这个假分位**。生长分位属医疗相关结论，宁可返回 `null` 也不给错值。

### 7.4 画像里的趋势措辞

`renderProfileBlock` 对最近两次测量的体重分位做**档位升降序比较**（`P3 < P15 < P50 < P85 < P97`）：升 → 「趋势上升」，降 → 「趋势下降」，同 → 「趋势平稳」。

## 9. 元信号与护栏：什么时候不该下结论

这是整条信号链里最容易做错、也最值钱的部分。核心口径三条：

### 9.1 「无记录」≠「数据陈旧」

| 情形 | 性质 | 助手应当 |
| --- | --- | --- |
| 母乳 0 条 | **有效结论**（确定已停） | 直接说已停止母乳 |
| 症状 31 天无记录 | **信息缺失** | 只能说"这段时间没有相关记录"，**不得**推断"没有过敏反应" |
| 辅食近 14 天无记录 | **信息缺失** | **不得**推断"种类不足" |
| 排敏 0 条建档 | **信息缺失** | **不得**说"还没开始排敏"或"都耐受" |
| 配方 3 天未更新 | **数据陈旧** | 引用构成时必须标注截至日期 |

### 9.2 覆盖率不足不下阴性结论

元信号覆盖率 < 50% 时，不产出阴性结论（设计口径，见 PRD-006 §4）。实现上由 `trust.symptomUsable` 与渲染层的「信息缺失」文本承载。

### 9.3 注入块自带的行为约束

前文 §5.6 / §6.8 已完整列出。要点复述：

- 不复述统计口径（条数/窗口/均值）
- 不把"无记录/陈旧"当阴性结论
- 不把现状当计划（不给目标、倒计时、待办）
- 医疗判断附免责

这三条决定了注入是否**真的改变回答**，而不是变成一段"资料"。线上对照实验的证据：关闭注入后，助手会把**已确认过敏的南瓜泥当普通食材列出**。

## 附录 C：改信号时的连带改动清单

改一处信号，往往要动多个文件。按信号类型对照：

| 改动类型 | 必须同步的位置 |
| --- | --- |
| 新增一个数据维度 | `query.js` 的 METRICS / METRIC_LABELS / SIMPLE_METRICS 三处 → `selectClause`（隐私列）→ `query-baby-data.js` 描述 → `analyze-baby-data.js` 的 digestPatch + buildWeeks → `profile.js` 新鲜度四处（若家长会连续记录） |
| 新增一个感知板块 | `perception.js` 查询函数 → 主入口组装 → `renderPerceptionBlock` → `buildFlags` → `verify-perception.mjs` 断言 → `perception-preview.mjs` 打印 → `TECH-014` |
| 调整参考值 | 只改 `REF`（唯一出处），但需同步 `TECH-014` 与 `RESEARCH-20260920` 的文字表述 |
| 调整新鲜度源清单 | **只改 `profile.js::FRESHNESS_LABEL`** —— 它是唯一出处，`perception.js` 与干跑脚本都从这里 import |
| 调整阶判断 | `profile.js::LADDER_LEVEL` / `NEXT_STAGE` |

**三条禁则**：

1. 同一语义的清单不得在多个文件各存一份（`FRESHNESS_LABEL` 曾三处并存，加一个维度要改三处）。
2. 干跑脚本不得自己重算算法，只能 import 同一份实现（否则"脚本对了、线上不对"）。
3. 可空对象的守卫必须贯穿所有消费点（`stage` 可为 null，漏一处就整段降级）。
