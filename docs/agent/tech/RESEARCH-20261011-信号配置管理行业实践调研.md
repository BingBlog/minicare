# RESEARCH-20261011 信号配置管理 · 行业实践调研

> 目的：为「minicare-agent 信号（感知信号）的配置与管理能力抽离到 minicare-platform 可视化维护」这一 PRD 提供行业参照。
> 范围：风控规则平台 / 医疗 CDSS 知识规则 / 配置中心 / Feature Flag / 告警规则 / 可视化规则编排（DMN），六个方向。
> 关联文档：`SIGNALS-20260921`（信号清单与口径）、`GAP-20260922`（缺口与补齐）、`TECH-013`/`TECH-014`（实现）、`PRD-006 §4`（设计）。

---

## 0. 结论摘要（先行）

行业里「把硬编码的判定逻辑与参数抽出来管理」是成熟命题，但**六个方向的解法各不相同**，共同收敛出的做法是：

1. **配置与执行解耦**：「规则/参数」成为数据，执行引擎保持不变（风控平台、配置中心、DMN 的共同底座）。我们的对应：`REF` 参考值、flag 规则参数、食物词表从 `perception.js` 抽出为数据。
2. **状态与生命周期分层**：草稿 → 灰度/影子 → 在线 → 离线，任何变更可回滚（配置中心、风控、Feature Flag）。改动不删代码、下线可配置。
3. **发布前必须有「验证」环节**：单元测试（该触发必触发、该沉默必沉默）、合成数据干跑、影子测试（Alertmanager `promtool`、CDSS 单测、风控影子流量）。我们已有 `verify-perception.mjs`（101 条断言）与 `perception-preview.mjs`（干跑），平台化后应成为变更流程的一环。
4. **医学类规则受法规级约束**：循证来源标注、审核发布流程、审计日志、定期复审（卫健委 CDSS 规范：更新周期不长于半年、知识有退出机制）。我们的参考值有循证出处（`RESEARCH-20260920`），配置化后每个值都应保留「证据锚点」。
5. **噪音治理是一等公民**：静默（带时长）、抑制（高优压低优）、频控、疲劳控制（「响应永远是'什么都不做'的告警就删掉」）。我们的 flag 频控（7 天去重 / 单轮 1 条 / 强弱分级）与之同构，但参数目前硬编码。
6. **不是所有配置都适合动态热更**：底层/高风险参数走完整发布流程（测试环境验证 → 灰度 → 全量），低风险参数才允许即时生效。我们平台（本机）与 agent（CloudRun）跨环境，此项直接决定「生效机制」设计。
7. **兜底是硬要求**：默认值 + 本地缓存 + kill switch，配置服务不可用时系统必须照常运行（Feature Flag、配置中心共识）。我们 `perception.js` 已有「失败静默降级」原则，配置化后需新增强制兜底：**配置文件损坏/缺失时必须回退内置默认值**。
8. **非技术可读性靠「表」**：决策表（条件列/动作列）、规则卡片是行业让非工程师参与维护的主流形态；但真正的规则引擎（DMN/Drools）对单人项目是过度设计——行业反模式显示，规则引擎引入的成本在「治理纪律」而非引擎本身。

## 1. 风控规则平台（美团 Zeus / 火山引擎智能风控）

### 1.1 美团 Zeus 的分层抽象

美团风控的演进路径与本项目高度同构：**最初策略硬编码在业务代码里**，随业务扩张出现「策略分散无法管理、逻辑同业务强耦合、更新受限于开发排期」，随后建设规则平台（来源：美团技术团队《复杂风控场景下，如何打造一款高效的规则引擎》）。

Zeus 的分层：

| 层 | 定义 | 我们的对应物 |
|---|---|---|
| 场景 | 规则集合（如「下单场景」） | 信号组（A-J 十组）或「转奶 / 排敏」业务线 |
| 规则 | 最小决策单元（命中/不命中） | 单个 flag（12 条）或判定路径（route） |
| 因子 | 可复用逻辑单元（表达式型/累计型/扩展型） | 单个信号（46 项） |
| 参数 | 因子计算依赖的输入 | 表字段 + `REF` 参考值 |

关键机制：
- **规则状态**：支持「标记 / 在线 / 离线」三态，方便测试和调整（下线一条规则不用改代码）。
- **标签系统**：对规则、场景、因子、参数做分类检索。
- **运行监控**：场景决策与规则命中效果监控、因子利用率/有效性监控。
- **影子测试**：新策略灰度验证后再全量上线；离线用历史数据回放验证。

### 1.2 火山引擎（字节）智能风控

- 可视化规则工厂：拖拽式规则配置，「设备异常+行为突变+地理位置」多条件组合，新规则上线约 10 分钟。
- 决策效果即时反馈：监控规则命中率与误伤率，AB 测试持续优化。
- 支持评分卡机制（加权组合）。

### 1.3 启示

- 分层概念（场景/规则/因子/参数）可以直接借用为**平台信息架构**：信号台账按「组 → 信号 → 参数」组织，flag 单独成区。
- 「命中率监控」思想：平台应能回答「某条 flag 最近有没有触发过、触发了几次」——目前只有干跑脚本能看单点，没有累计视图。
- 但我们**不做**：多角色运营、AB 测试、实时风控引擎。单人单宝宝场景，规模不符。

## 2. 医疗 CDSS 知识规则管理（最相关的对标域）

### 2.1 国家卫健委《医疗机构临床决策支持系统应用管理规范（试行）》（2023-08）

对知识库的要求（法规级，原文要点）：

- **来源权威性**：临床知识来源应是法律法规、临床路径、诊疗指南、专家共识、医学教材、文献等。
- **更新周期**：知识库应及时更新，**更新周期一般不长于半年**；知识库内容应有**退出机制**（不适用的知识及时删除或更新）。
- **审计**：CDSS 使用应留存审计日志，可溯源评价。
- **管理流程**：医疗机构应明确知识搜集、**规则编写、审核发布**、反馈评估的流程与制度。

### 2.2 CDSS 知识库的工程实践（Basalt / NCBI / 江苏省人民医院）

- **证据分级嵌入规则元数据**：GRADE 框架（High/moderate/low/very low + Strong/conditional），引擎按证据强度排序/过滤提示。→ 规则不是「一个值」而是「值 + 证据等级 + 出处」。
- **知识表示标准**：Arden Syntax、CQL——把规则写成**人类可读**的形式，非程序员可审阅。→ 我们的「flag 规则卡片」可以借鉴：用自然语言伪代码展示规则逻辑（而非 JSON）。
- **版本控制与变更管理**：commit 历史（时间、作者、理由）、分支（实验规则不影响生产）、tag（稳定版本绑定指南版本）、变更请求工作流（同行评审、影响分析、测试后上线）。
- **质量保证**：单元测试——「规则在预期条件下触发、其余情况保持沉默」；上线前验证、金标准对比。
- **知识架构显式化**：NCBI 建议厂商明确「知识库与系统如何交互」，且**用户的自定义不受产品升级影响**（customization survives updates）——这与我们「配置 vs 代码升级」的关系设计直接相关。

### 2.3 启示

- 我们的 REF 参考值本质是「带循证出处的临床参数」，应当：**每值带出处与证据描述**（现有 RESEARCH-20260920 已有一半），变更**记录理由**，且支持**定期复审提醒**（半年周期太重、单人场景可做成「上次审阅时间 + 提示」）。
- 「规则在预期条件下触发、其余情况保持沉默」正是我们 101 条断言的形态，平台化后断言应在「变更 → 发布」链路中被强制执行（改动 flag 参数 → 自动跑相关断言）。
- 「用户自定义不受升级影响」：我们的配置与代码必须是**可分离升级**的——配置文件在、逻辑升级不丢配置；这也是「文件为真源」方案的一个论据。

## 3. 配置中心（Apollo / Nacos）

### 3.1 核心机制

| 机制 | Apollo | Nacos | 对我们的意义 |
|---|---|---|---|
| 热发布/推送 | 长轮询 + 内存缓存 | 长轮询/UDP | 本机→CloudRun 跨环境，此机制不直接适用（见 §8 生效机制） |
| 灰度发布 | 按 IP/集群，多维 Fine-grained | Beta（IP 列表）/Tag | 单人场景不需要灰度用户，但「先验证再全量」的流程思想适用 |
| 版本管理 | **完整历史 + diff + 一键回滚** | 基础版本 | 平台应提供「版本快照 + diff + 回滚」 |
| 审计日志 | 操作审计（谁、何时、改了什么） | 较弱 | 必须有——尤其医学参数 |
| 兜底 | 本地文件缓存（网络断可启动） | 内存缓存 | 强制：配置文件缺失/损坏时回退内置默认 |
| 权限 | 细粒度 RBAC | 基础鉴权 | 单人场景可省略 |

### 3.2 生产变更 SOP（社区共识）

- 变更流程：**测试环境验证 → 灰度发布 → 全量发布**；变更前记录原值，变更后观察 5-10 分钟确认无异常。
- 「动态刷新虽好，不是所有配置都适合动态刷新」：数据库连接串这类底层参数应走完整发布流程；只有运行参数适合动态调整。
- 配置变更接入监控告警：发布即通知，便于回溯。
- 配置中心一旦引入就是基础设施：稳定性第一，单机跑是事故预备。

### 3.3 启示

- 「变更前记录原值、变更后观察」直接映射为：**平台保存变更快照 + 变更后干跑对比（改前/改后注入块 diff）**。
- 「哪些配置适合热更、哪些必须走发布」——我们的分级预判：
  - **低风险（可即时）**：词表增删（别名/后缀）、展示文案。
  - **高风险（走发布+验证）**：医学参考值（14 天/3 天等）、频控参数、判定顺序。
- 单人项目不需要 RBAC/审批流，但「审计日志 + 变更理由」保留。

## 4. Feature Flag 平台（LaunchDarkly）

### 4.1 三段式生命周期

- **Define**：定义 flag 行为（布尔/多变量），自定义规则与前置条件（prerequisite），**预览影响（Preview targeting / simulate impact）——上线前看到谁会被影响**。
- **Target**：多维度定向、渐进发布（progressive rollout）、环境门控。
- **Control**：实时更新（<200ms）、**kill switch（一键关停）**、**自动回滚（基于指标或观测信号）**。

### 4.2 关键工程实践

- **Fail-safe 兜底**：SDK 把 flag 值与规则缓存在内存/本地，「即使配置服务宕机，应用照常运行（用默认值）」。
- **环境 diff**：跨环境对比 flag 配置差异（dev/staging/prod 漂移可见）。
- **Flag 债务治理**：flag 有生命周期终点的概念（上线稳定后清理），平台提供「何时可安全清理」的状态提示。
- **审计 + 变更跟踪**：全量审计日志、approval policies、环境间变更跟踪。

### 4.3 启示

- **预览影响**是平台化的核心卖点之一：改动一个阈值前，看到「用真实数据跑一遍，哪些 flag/判定会变化」——对应我们的「干跑对比」。
- **kill switch**：每条 flag 的独立开关 + 全局注入开关（已有 `PERCEPTION_INJECT`/`FLAG_THROTTLE` 两个，平台化后把开关体系做全）。
- **环境 diff**：本机开发库（minicare_dev）与生产库（旺仔数据）跑同一份配置的差异视图——超出本期范围，但「dev/生产同一份配置」的一致性要保证。

## 5. 告警规则管理（Prometheus Alertmanager）——机制同构度最高

### 5.1 与信号 flag 的同构对照

| Alertmanager 机制 | 我们的对应 | 现状 |
|---|---|---|
| 告警分级（critical/warning/info） | flag 强度（strong/medium/weak/intercept） | 已有，硬编码 |
| `inhibition`（高优告警触发时抑制低优） | 「强项不受频控、先看强度再看顺序」 | 已有（pickFlagsForTurn），硬编码 |
| `silence`（**必须带时长**，防遗忘） | flag 7 天去重（冷却窗口） | 已有（进程内），窗口硬编码 |
| `repeat_interval`（重复提醒节奏） | 同 flag 冷却后重提醒 | 同上去重机制 |
| 疲劳控制原则 | §4.5「单轮 ≤1 条非强项」 | 已有，硬编码 |

运维社区共识（值得抄进设计）：
- **Silence 必须设过期时间**——「没有期限的静默会在若干天后变成漏报」。
- **「如果一条告警触发后的正确响应永远是'什么都不做、等它过去'，删掉它」**——我们的对应：一条 flag 如果长期只产生噪音没有行动价值，应降级或下线（平台应能观察到「这条 flag 触发过几次、有没有对应的行动」，至少提供触发次数统计）。
- **告警规则要版本化、存 Git、变更评审、staging 先跑**（以 info 级运行一周，确认无误报再升级）——**「新 flag 先以弱强度上线，观察后再升级强度」**是同款思路。

### 5.2 promtool 单测（验证模式直接可抄）

```
tests/alert_test.yml：
  合成输入序列（模拟 20 分钟数据）→ eval_time: 10m
  → 断言 HighErrorRate 在 10 分钟时触发（exp_alerts）
```

对应我们的断言形态：合成 perception 输入（或真实宝宝数据快照）→ 断言该触发的 flag 触发、该沉默的 flag 沉默。平台化后「编辑配置 → 自动跑断言集」应成为保存前置条件。

## 6. 可视化规则编排（DMN / 决策表 / GoRules）

### 6.1 主流形态

- **决策表（DMN Decision Table）**：条件列 + 动作列 + 命中策略（first/hit policy），非技术人员可直接读写；工具会在编辑时检查**缺口（gap）/重叠（overlap）/冲突**（Trisotech、Camunda）。
- **GoRules**：现代轻量方案，**JSON 进 JSON 出** + 浏览器可视化编辑器 + **决策 trace**（每个运行结果可回溯到具体命中了哪条规则条件）——用于生产决策的可调试性。
- **Drools/OpenRules**：Excel/表格承载规则，编译执行。
- 行业对比反复提示的两个坑：
  1. **模拟与运行时必须同一套规则**（否则「测试过了、线上不一样」）；
  2. **规则表变大后治理复杂度飙升**——需要命名、分层、评审纪律，否则「一坨表格」比代码更糟。

### 6.2 启示

- 我们**不做**规则引擎（理由：单人项目、flag 条件涉及跨表派生（如「过敏食材 × 近 14 天食用记录」），不是简单条件组合；行业教训显示引擎化的成本在治理而非技术）。flag 触发逻辑继续留在代码。
- 但「规则卡片」值得做：**平台以只读方式呈现每条 flag 的完整定义**（自然语言描述 + 触发条件伪代码 + 强度 + 关联参数 + 证据/出处 + 最近触发记录），成为「改参数前先读懂规则」的入口。
- 「决策 trace」启发：干跑结果应能追溯到「哪些输入信号 → 触发了什么判定」—— `perception-preview.mjs` 已有雏形，平台化后结构化呈现。

## 7. 横向模式提炼

### 7.1 六个方向共同收敛的做法（按重要性排序）

1. **参数与逻辑分离**，参数成为可管理的数据（全部六个方向）。
2. **变更的生命周期管理**：草稿 → 验证 → 发布 → 在线 → 下线，全链路留痕（风控/配置中心/Feature Flag）。
3. **变更前验证的三件套**：单测断言（promtool/CDSS）、干跑/模拟（风控回放、LD preview）、影响面预览（LD simulate）。
4. **审计与可回溯**：谁、何时、改了什么、为什么、影响什么（全部；CDSS 为法规要求）。
5. **兜底与降级**：配置不可用时回退默认值，系统不因配置故障而故障（配置中心/Feature Flag）。
6. **噪音治理机制**：静默（带时限）、抑制、频控、分级（Alertmanager 最系统化）。
7. **证据/理由元数据**：医学规则带证据等级与出处（CDSS 独有，但对我们是刚需）。

### 7.2 反模式（明确不做/避免）

- ❌ **为配置而配置**：把「逻辑」（复杂条件树）也塞进配置表单 → 变成不可读的配置地狱（决策表大型化教训）。
- ❌ **动态热更一切**：底层/高风险参数即时生效、无版本、无回滚 → 事故来源（配置中心共识）。
- ❌ **模拟与运行时两套实现**：测试过的和线上跑的不是同一份 → 最隐蔽的坑（SIGNALS 附录 C 已有同款禁则）。
- ❌ **配置服务成为单点**：配置读取故障导致业务故障（必须兜底）。
- ❌ **沉默配置**：改了什么没人知道、没法回滚（CDSS/配置中心都要求审计）。

## 8. 对 minicare 的映射与取舍（PRD 设计输入）

### 8.1 现状 vs 行业标准（差距表）

| 能力 | 行业标准做法 | minicare 现状 | 差距性质 |
|---|---|---|---|
| 参数集中管理 | 配置中心/规则平台可视化 | `REF` 等 8 类配置硬编码在 `perception.js` 等 3 个文件 | **主差距（本 PRD 解决）** |
| 变更验证 | 单测 + 干跑 + 预览 | 有断言（101 条）与干跑脚本，但与「改配置」不联动（改完手动跑） | 流程缺环 |
| 版本与回滚 | 快照 + diff + 一键回滚 | 依赖 git 手工操作 | 主差距 |
| 审计 | 操作日志 + 理由 | 无（git commit 可选写理由） | 主差距 |
| 证据标注 | 规则带证据等级/出处 | `RESEARCH-20260920` 有出处但只有文档级，未与代码值绑定 | 半差距 |
| 噪音治理参数 | 可配置（silence/抑制） | 机制已有、参数硬编码（7 天/1 条/强项豁免） | 半差距 |
| 兜底降级 | 默认值 + 缓存 | 已有「失败静默降级」（查询失败组置空）+ `Object.freeze(REF)` | 基本满足，配置化后需保持 |
| 生存周期终点的治理 | flag 债务清理 | 无（新增 flag 靠 PRD 修订） | 可选项 |

### 8.2 关键设计决策（PRD 需拍板）

1. **真相源方向**：
   - 方案 A：平台编辑 → 导出回写 `minicare-agent/config/signals.yaml`（**文件即真相源**，agent 运行时读文件、缺失回退内置默认）——配置可 git 审计、随部署发布。
   - 方案 B：平台 DB 为真相源 → 同步机制推送到 agent（需新建跨环境分发链路）。
   - 倾向 A：符合「单一真相源」「配置可分离升级」原则，且单人场景下不需要毫秒级分发。
2. **生效机制**（本机平台 → CloudRun agent）：
   - A-1：配置文件随 Docker 镜像部署（低频、稳、慢，与现有部署 SOP 衔接）。
   - A-2：配置发布到云端存储（COS/CloudBase DB），agent 启动/定期拉取（快，需新链路 + 缓存兜底）。
   - 倾向一期 A-1（部署即生效），二期视需要再补 A-2。
3. **配置化范围边界**（一期界定）：
   - ✅ 做：参考值参数（REF 18 项）、频控参数（去重窗口/单轮条数/强项豁免）、flag 独立开关与强度、食物词表（高致敏分组/七大类/前后缀/别名）、注入开关。
   - ⚠️ 谨慎：flag 触发条件（一期不配置化，只读展示 + 参数引用）、判定优先级链顺序（可配置顺序但需强校验）。
   - ❌ 不做：枚举映射（`SYMPTOM_TYPE_LABEL` 等——有「唯一出处」约束，指向后端 DTO/小程序 constants，配置化会造成双源漂移）、prompt 静态模板（除动态渲染段外）。
4. **验证联动**：平台保存/发布配置时自动运行相关断言；干跑对比（改前 vs 改后注入块 diff）作为必看环节。
