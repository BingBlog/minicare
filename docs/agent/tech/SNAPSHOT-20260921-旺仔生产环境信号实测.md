## 8. 交叉核对与发现

### 8.1 数据面：一条完整的时间线

把各维度拼起来，能还原出**一次辅食排敏的完整过程**，而它正好横跨了三个维度的信号：

| 日期 | 事件 | 落在哪个信号 |
| --- | --- | --- |
| 2026-09-14 | 首次引入牛肉（记录 2 次） | `food_observation` → 09-20 判 safe |
| 2026-09-15 | 首次引入三文鱼泥（`intro_count=1`） | `food_observation` + `feeding_food_item` 逐日 |
| 2026-09-19 16:39 | 开始服药：蒙脱石散 + 妈咪爱 | `medication_record` |
| 2026-09-20 19:07 | 继续服药 | `medication_record` |
| 2026-09-20 23:33 | 火龙果判 `allergic`（moderate） | `food_observation` |
| 2026-09-20 23:34 | **三文鱼泥判 `allergic`（severe，diarrhea）** | `food_observation` + `health_record` |
| 2026-09-21 08:17 | 蒙脱石散加量至 1 袋 | `medication_record` |
| 2026-09-21 | 转奶判定「具备推进条件（需无症状前提）」 | `perception.stage.verdict` |

**这里有一处值得注意的张力**：感知层给出的判定是「本阶已 30 天 ≥ 参考 14 天，具备推进条件（**需无症状前提**）」，但同一时刻宝宝正在腹泻用药（09-19 起连续 3 天）、且前一天刚把三文鱼泥判为 severe 过敏 —— **「无症状前提」实际不成立**。

**两条链路同时错过了同一个事实**：

| 链路 | 实际内容 | 为什么没进入判定 |
| --- | --- | --- |
| `symptom_record`（感知层的症状来源） | 全表仅 4 条，最后一条 **2026-08-19**（喷射性呕吐） | 33 天无记录 → 被元信号判为「不可用」，明确禁止据此下结论 |
| `health_record.allergy_symptoms`（真实的腹泻证据） | 全表 4 条过敏反应：05-02 皮疹/湿疹 mild、05-29 生菜 diarrhea mild、09-05 芹菜 other mild、**09-20 三文鱼泥 diarrhea severe** | 该字段**未进入现状感知的任何判定**，既不是症状来源、也不是转奶前提 |
| `medication_record`（正在对症用药） | 09-19 起蒙脱石散 + 妈咪爱，共 5 次 | 只进了画像新鲜度，不进任何前提检查 |

而 `perception.js` 的转奶判定只看**配方构成稳定天数**，不看症状、不看服药、也不看近期的过敏反应记录。

这是本轮实测发现的**最有价值的问题**：`health_record.allergy_symptoms`（观测反应）与 `food_observation` 本来就是联动的（该表带 `observation_id` 外键、`reaction_source=observation`），但它没有进入现状感知的症状判定，也没进 `stage` / `maintain` 的任何前提检查。建议列进「感知层完整版」的矛盾 flag，例如 `stage_ready_but_symptomatic`。

### 8.2 三处口径问题

**① `health` 维度把体温"加总"，导致异常点误报（最该修）**

`analyze_baby_data` 近 30 天报了 5 条异常，其中 **3 条是健康维度的假阳性**：

| 日期 | 报的数值 | 对照均值 | 真相 |
| --- | --- | --- | --- |
| 2026-08-25 | 110.5 | 18 | 当天 3 次体温 37.0+36.7+36.8 = 110.5，被当成"日合计" |
| 2026-08-28 | 36.4 | 85 | 单次体温，被拿去和"体温合计"比 |
| 2026-09-08 | 143.4 | 12 | 当天 4 次体温之和 |

体温是**点测量值**，日合计无物理意义，`sum`/`total` 口径在健康维度不成立。只有 2 条异常（09-16、08-25 的睡眠）是真的。建议：健康维度要么不参与异常点检测，要么改用日均值而非日合计。

**② `system.js` 规则 5 的 metric 清单漏了 `medication`**

`src/prompts/system.js:56` 写的是 8 个维度：

```text
按需选 metric（feeding/sleep/diaper/growth/health/symptom/activity/medical）与时间窗（days）
```

实际 `METRICS` 有 **9 个**（已含 `medication`）。工具自身的 description 里有服药，所以模型仍可能调用；但 prompt 白名单没列，属于**提示层面的不一致**，建议补上。

**③ 画像段渲染 7 个新鲜度源，感知段渲染 8 个**

`profile.js:555` 的渲染顺序是 `['formula','food','supplement','medication','growth','symptom','medical']` —— **不含 `diary`**；而 `profile.freshness` 里有 `diary`（2026-09-19），感知段的 `trust.sources` 也把它渲染出来了（「日记2天前」）。

结果：同一份新鲜度数据，两段注入文本一个显示 7 项、一个显示 8 项。**不是数据错，是渲染口径不一致**，建议统一（要么 profile 渲染补上 diary，要么感知段也不渲染）。
