# 知识图谱构建开源工具调研

> 生成时间：2026-08-19 ｜ 目的：为敏宝知识库（20 份中文/英文医学文献，8 模块 40 条目，中小规模）选型
> 调研范围：图数据库、LLM 图谱构建流水线、实体关系抽取、本体/语义、可视化

---

## 一、工具全景（5 大类）

### 1.1 图数据库 / 存储（存哪里）

| 工具 | 开源协议 | 语言 | 特点 | 适用 |
|---|---|---|---|---|
| **Neo4j 社区版** | GPLv3 | Java | 最流行、Cypher 查询、文档友好、医疗项目成熟案例多 | 中小规模首选（本类推荐） |
| **NebulaGraph** | Apache-2.0 | C++ | 国产、分布式、万亿边级、图算法丰富 | 大规模 |
| **JanusGraph** | Apache-2.0 | Java | 分布式、可接 ES/Solr、横向扩展 | 超大规模 |
| **Kuzu** | MIT | C++ | 嵌入式、单机极快、OLAP 查询、Python 友好 | 轻量单机 |
| **Apache AGE** | Apache-2.0 | C | PostgreSQL 图扩展、兼容 Cypher | 已有 PG 环境 |
| **Memgraph** | BSL（部分） | C++ | 内存图、实时分析 | 实时场景 |

### 1.2 LLM 图谱构建流水线（文本 → 图谱 → RAG）

| 工具 | 特点 | 成本/更新 | 适用 |
|---|---|---|---|
| **Microsoft GraphRAG** | 社区发现+全局问答强、可解释 | 构建贵、不支持增量 | 大规模（10K+ 文档）全局理解 |
| **LightRAG**（港大/北邮） | 轻量、Token 消耗约为 GraphRAG 1/6000、**支持增量更新**、双层检索 | 低 | **中小规模动态数据首选**（本类推荐） |
| **HippoRAG** | 类海马体长期记忆、PageRank 检索 | 中 | 长期记忆/多跳 |
| **KGGen**（Python, MIT） | 三阶段（生成→聚合→聚类）、自动实体归并、MINE 指标 66%（超 GraphRAG 18%） | 中 | 高质量稠密图 |
| **Cognee** | 端到端构建+检索、图+向量融合、中文支持一般 | 中 | 通用知识增强 |
| **Fast-GraphRAG** | 简化部署 | 低 | 快速原型 |

### 1.3 中文实体关系抽取（关键环节，中文医学）

| 工具 | 来源 | 特点 | 推荐度 |
|---|---|---|---|
| **OpenSPG** | 蚂蚁集团 | **端到端图谱构建平台**（Schema→抽取→存储→查询），集成 OneKE，SPG 语义建模 | ⭐⭐⭐⭐⭐ 国产平台首选 |
| **OneKE** | 蚂蚁+浙大 | **中文 LLM 统一抽取框架**（NER/RE/EE），基于 Chinese-Alpaca-2-13B 微调，支持医学场景 | ⭐⭐⭐⭐⭐ 中文抽取首选 |
| **DeepKE** | 浙大+蚂蚁 | 静态/零样本/少样本多范式，NER/RE/EE 全流程，中文好 | ⭐⭐⭐⭐ 灵活研究 |
| **HanLP** | 汉语言技术 | 中文分词/依存/命名实体，Java/Python | ⭐⭐⭐ 传统 NLP |
| **LTP**（哈工大） | HIT | 中文词法/句法/语义分析 | ⭐⭐⭐ 传统 NLP |
| **PaddleNLP / UIE** | 百度 | 通用信息抽取，预训练 | ⭐⭐⭐ |

## 二、针对敏宝的推荐组合

### 场景约束（敏宝实际）
- 规模：20 份文档（~400 页），40 个知识条目 → **典型中小规模**
- 语言：中文为主（含英文指南）
- 更新频率：资料季度/年度级（新指南发布）
- 后续需求：检索增强问答（RAG）、家长问答
- 技术栈：腾讯云 CloudBase 生态（若落地）

### 推荐方案（分两档）

**方案 A：轻量快速（建议先落地）**

```
抽取与构建：LightRAG 或 OneKE + DeepKE（中文医学抽取）
存储：LightRAG 内置图（或 Kuzu 嵌入式） + 向量
RAG：LightRAG 双层检索（局部细节 + 全局主题）
可视化：Cytoscape.js / ECharts 关系图
```

> 理由：20 份文档规模下，LightRAG 30-80ms 查询、增量更新、Token 成本极低；OneKE/DeepKE 中文医学抽取开箱即用。

**方案 B：平台级（需要长期运维）**

```
构建平台：OpenSPG（蚂蚁）—— Schema 定义 → OneKE 抽取 → 图存储 → 查询全链路
存储：OpenSPG 内置 / NebulaGraph
问答：OpenSPG + 自研 RAG 链路
```

> 理由：要"平台化、Schema 驱动、多轮迭代"时，OpenSPG 是国产最完整方案，医疗/金融均有落地案例。

**不建议**：直接上 Microsoft GraphRAG（对 20 份文档规模过重、不支持增量、成本高）。

## 三、选型决策速查（按你下一步动作）

| 你的下一步 | 推荐工具 | 理由 |
|---|---|---|
| 只想先把图谱跑起来看效果 | **LightRAG** | 一条命令索引文档，自动抽取+检索+可视化 |
| 要精细控制中文医学实体 | **OneKE / DeepKE** | 中文 LLM 抽取，医学可微调 |
| 要"正规军"图谱平台 | **OpenSPG** | 端到端，Schema 驱动，国产社区 |
| 要存储+手工 Cypher 查询 | **Neo4j 社区版** | 最成熟，可接 LangChain/LlamaIndex |
| 已有 PostgreSQL | **Apache AGE** | 免新装数据库 |
| 要做图谱可视化给用户看 | **ECharts 关系图** | minicare 已有 ECharts 基础 |

## 四、落地路线（结合敏宝现状）

```
已有：20 份源文件 → 已解析纯文本（源文件解析文本/）
      知识图谱概念层设计（实体/关系/概念字典）

Step 1  概念层落库：按《知识图谱-概念层设计》定义 Schema
        → OpenSPG SPG Schema 或 LightRAG 实体类型配置
Step 2  实体关系抽取：用 OneKE/DeepKE 对已解析文本跑抽取
        → 产出三元组草案（LLM 结果须人工+医学审核）
Step 3  审核入库：高危关系（治疗/禁忌/诊断）逐条审核
Step 4  检索对接：LightRAG 双层检索 或 OpenSPG+向量
        → 接入《召回质量测评方案》验证
Step 5  可视化：ECharts/Cytoscape 展示 CMPA 子图
```

**关键提醒**：
1. LLM 抽取结果**必须医学审核**（医疗关系错代价高）
2. 三元组需标注来源文档+页码（延续溯源原则）
3. 概念字典（口语→医学概念）是全链路地基，持续扩充
