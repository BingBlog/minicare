## 一、项目是什么

**minicare**（中文产品名：**敏宝日记**，英文名 **MimiCare**）是一款专为过敏体质婴幼儿（简称"敏宝"）家庭打造的健康记录与护理管理平台。

核心使命：把敏宝家庭日常的**饮食、转奶、症状、睡眠、生长**等护理信息结构化地记录下来，自动生成可分享的数据分析报告，帮助家长科学排敏、高效就医、全家协同。

一句话概括：**敏宝家庭的结构化健康记录工具 —— 让"记录"变得极简，让"就医沟通"变得高效。**

项目现状：

- **MVP 已完成并上线**：以微信小程序为主分发平台，已于 2026-04-28 发布上线
- **代码仓库**：Monorepo 结构（后端 API + 小程序 + Web 三包独立）
- **平台策略**：微信小程序为主平台，Web 端为早期原型平台（维护模式）

## 二、项目背景与缘起

### 2.1 市场背景

- 中国 0-6 岁婴幼儿中**过敏体质占比约 15%**，对应敏宝家庭规模**超 1200 万**，且每年以约 8% 的速度增长
- 牛奶蛋白过敏（CMPA）是中国婴幼儿最常见的食物过敏类型之一，确诊患病率约 2.69%
- 敏宝家庭每年在特殊配方奶粉上的支出可达 2.5 万元，比普通奶粉高出 1 万元以上
- 国内母婴 APP 付费渗透率约 18.7%，垂直护理工具的付费意愿明确

### 2.2 核心痛点

1. **排敏无规范记录**：辅食添加、转奶过程缺乏系统化记录手段，全凭记忆
2. **过敏原与症状无法关联**：难以回溯"吃了什么 → 出现了什么反应"
3. **就医沟通成本高**：就诊时需手动整理零散记录，信息不完整
4. **祖辈参与门槛高**：71.8% 的婴幼儿由祖辈承担主要照料，但复杂 APP 让老人难以上手
5. **现有产品不匹配**：综合母婴 APP（宝宝树、亲宝宝）功能繁杂、广告多、无敏宝垂直能力

### 2.3 项目缘起

项目源自**创始人家庭自身的真实需求**——团队本身就是敏宝家庭，在养育牛奶蛋白过敏宝宝的过程中，深切体会到现有工具的不足，决定亲手打造一款"自己会用、家人能用、医生认可"的敏宝护理记录工具。因此产品从第一天起就以真实场景驱动：极简操作、全家适配、数据安全、就医友好。

## 三、目标用户

| 用户群 | 特征 | 核心诉求 |
|---|---|---|
| **核心用户（父母）** | 25-35 岁敏宝父母，本科及以上学历，注重科学育儿 | 精准排敏、症状追踪、就医同步、数据安全 |
| **协作用户（祖辈/保姆）** | 50-65 岁，参与日常照料，智能手机操作不熟练 | 简单直观、大字体、少打字、语音输入 |

中国家庭普遍是"2+2+1"（两位老人 + 两位父母 + 一个孩子）的多代同堂照护模式，产品设计必须同时服务两代人——这是 minicare 与其他母婴工具最大的体验差异点。

## 四、产品定位与核心价值

### 4.1 产品定位

垂直敏宝护理记录工具，主打 **"极简、精准、全家适配"**，聚焦排敏、症状追踪、生长监测三大核心场景，拒绝广告干扰。

### 4.2 五大核心价值

1. **全场景记录**：覆盖饮食、睡眠、活动、尿布、健康、表现、生长、医疗 8 大类敏宝护理场景
2. **结构化管理**：记录模板符合医学记录标准，数据可一键生成多维分析报告供医生参考
3. **家庭协作**：手机号邀请家庭成员，多人实时同步记录同一宝宝的护理数据
4. **代际友好设计**：大字体模式 + 语音输入 + 选项快选，祖辈零门槛上手
5. **数据安全**：三层鉴权体系，健康数据加密传输存储，密钥仅存于服务端环境变量

### 4.3 与竞品的差异化

| 竞品 | 劣势 | minicare 差异化 |
|---|---|---|
| 宝宝树（综合母婴） | 功能繁杂、广告多，无敏宝垂直能力 | 垂直聚焦敏宝，极简无广告，适配祖辈 |
| Anti-敏宝排敏助手（垂直类） | 无生长监测/睡眠记录，无大字体模式 | 全场景记录覆盖 + 家庭共享 + 代际友好 |

## 五、核心功能

### 5.1 宝宝档案管理

创建/编辑宝宝档案：姓名、出生日期、性别、**过敏类型**（默认牛奶蛋白过敏）、**过敏程度**（轻度/中度/重度/未知，附 CDC 评分标准参考）。

### 5.2 八大记录模块

| 模块 | 说明 |
|---|---|
| **饮食记录** | 4 个子类型：配方奶 / 母乳 / 辅食 / 营养素。配方奶支持**多奶粉配比记录**（如 3 勺深度水解 + 1 勺氨基酸，自动计算比例）、奶量快选、24 小时总奶量统计 |
| **睡眠记录** | 一键计时模式（自动算时长）+ 手动补录；计时中断恢复、超 12 小时异常标记等状态机处理 |
| **尿布记录** | 大便次数/性状（内置 Bristol 分级参考）、小便尿湿程度，支持拍照留档 |
| **健康记录** | 过敏表现（皮疹/呕吐/腹泻/咳嗽/喘息/湿疹）、用药、保湿护理 |
| **表现记录** | 心情（情绪图标）、精神状态（活跃/正常/安静） |
| **活动记录** | 抬头、翻身、爬走、视力、运动、户外活动等 |
| **生长记录** | 身高/体重/头围，自动生成生长曲线，对比**中国 2023 儿科生长参照标准（P3-P97 百分位）** |
| **医疗记录** | 儿保/过敏检查/就诊，病历拍照上传（医疗模块支持 OCR 提取关键字段） |

### 5.3 敏宝专属业务规则（临床参考）

产品内置了基于权威指南（中华医学会儿科学分会 CMPA 诊治循证建议、ESPGHAN 2012、中国居民膳食指南 2022）的业务规则，所有提示均附注"请以就诊医生建议为准"：

**① 转奶路径管理**

```
氨基酸奶粉（稳定期 6~12 个月）
    ↓ 2~4 周混合过渡期
深度水解奶粉（稳定期 3~6 个月）
    ↓ 2~4 周混合过渡期
适度水解奶粉（稳定期 3 个月）
    ↓ 2~4 周混合过渡期
普通奶粉（达成免疫耐受）
```

- 混合过渡比例按每 2~3 天调整（25% → 50% → 75% → 100%）
- 升级条件：当前阶段稳定期达标 + 连续无表现 ≥ 14 天 + 生长发育正常
- 过敏反应回退机制：轻度退回上一步混合比例、中度退回上一完整阶段、重度立即退回氨基酸奶粉
- 转奶进度按阶段加权计算，仅在家长主动记录"今日无表现"后累加

**② 辅食新食物观察期状态机**

```
[未引入] → 首次记录 → [观察期中]（默认5天，可调3~7天）
  → 无异常+用户确认 → [已耐受]
  → 出现可疑表现 → [疑似过敏]（建议4周后白天少量重试）
  → 再次出现表现 → [确认过敏]（建议就医，6个月内不主动引入）
```

- 八大高风险过敏原（牛奶、鸡蛋、花生、坚果、鱼类、甲壳类、小麦、大豆）首次引入时额外风险提示
- 建议每次只引入一种新食物，便于排查过敏来源

### 5.4 家庭共享与多成员协作

- **手机号邀请**：创建者输入对方手机号 → 对方登录后自动加入
- **三级权限**：创建者（管理成员/改档案，唯一不可转让）＞ 编辑者（查看+新增记录）＞ 查看者（仅浏览）
- 每条记录标识记录人（如"妈妈记录""奶奶记录"），实时同步云端

### 5.5 数据分析报告

统计页支持 5 个维度的图表可视化（**饮食 / 尿布 / 生长 / 睡眠 / 健康**），基于 ECharts 6 实现，支持多时间范围切换（单日/一周/双周/月度/自定义），为就医沟通提供数据支撑。

### 5.6 体验设计要点

- **首页今日概览**：今日奶量/睡眠/尿布统计卡片（2026-10-09 起收敛为 3 项，原「今日用药」已下线）+ 今日时间线，3 次点击内到达任何核心功能
- **自定义 TabBar + 中心 FAB**：底部 4 Tab，中间浮动按钮弹出全部记录类型快捷入口
- **五种输入方式**：手动输入、自然语言（口语化描述自动解析结构化字段）、语音、拍照/图片、选项快选；识别结果以"解析确认卡片"形式让用户核对后再保存
- **大字体模式**：一键切换，全站文字按钮自动放大，适配祖辈视力
- **游客预览模式**：未登录用户可浏览首页布局，操作时引导登录

## 六、技术架构

### 6.1 架构全景

```
客户端层
├── 微信小程序（主平台）：Taro 4.2 + React 18 + ECharts 6 + TS
└── Web H5（维护模式）：React 18 + Vite 6 + Tailwind + PWA
        │ HTTPS REST API（JWT Bearer）
        ▼
腾讯云 CloudBase
├── CloudRun（minicare-api）：Node.js 20 · NestJS v10 · TypeScript
│   ├── 模块：auth / family / baby / records(8类) / storage /
│   │         websocket / scheduler / baby-foods / report / app-config
│   └── 鉴权链：JwtGuard → FamilyMemberGuard → RoleGuard(@MinRole)
├── CynosDB Serverless MySQL（约 18 张表）
├── 云存储 + CDN（照片/头像）
└── CloudBase Auth（手机号短信验证码登录）
```

### 6.2 Monorepo 结构（三个独立包，无根 package.json）

| 目录 | 技术栈 | 角色 |
|---|---|---|
| `minicare-server/` | NestJS v10 + TypeScript + mysql2（直连，无 ORM） | 后端 API，部署于 CloudRun |
| `minicare-mp/` | Taro 4.2 + React 18 + TypeScript | **微信小程序，主平台** |
| `minicare-web/` | React 18 + Vite 6 + Tailwind | Web 前端，维护模式 |

### 6.3 数据库设计

- 约 18 张表，分层依赖：`user_account`（账户）→ `family_group/family_member`（家庭）→ `baby_profile`（宝宝）→ 业务记录层（均含 `baby_id` + `recorded_by`）→ 衍生逻辑层（`food_observation` 辅食观察期状态机）
- 主键全部 CHAR(36) UUID；枚举字段 VARCHAR 存储；时区固定 UTC+8
- **喂养记录 4 表拆分**（母乳/配方奶/辅食/营养素独立成表）+ 2 张明细表（`formula_mix` 奶粉配比、`food_item` 食物明细），避免大量 NULL 列

### 6.4 关键架构决策

| 决策 | 理由 |
|---|---|
| 选微信小程序为主平台 | 零安装门槛（适配祖辈）、微信生态内分享传播（家庭协作场景）、扫码即用；Taro 保留跨端扩展能力 |
| 选 NestJS 而非 Fastify/Express | 多层权限模型（3 层 Guard × 多表 × CRUD）需要声明式装饰器复用 |
| ECharts Canvas 截图模式 | 规避微信小程序 Canvas 层级覆盖与滚动延迟的平台固有问题，离屏渲染后转 Image 展示 |
| 分包加载 | 主包仅含 4 个 TabBar 页面，登录/表单等全部放 subPackages 按需加载，优化首屏体积 |
| 双认证模式 | 开发环境 test 模式（固定验证码），生产环境 CloudBase SMS OTP + 后端 JWT（30 天有效期） |
| 全局配置缓存 | `/api/config` 枚举配置缓存到本地 Storage，避免重复请求 |

### 6.5 安全设计

- 三层鉴权：JWT 验签 → 家庭成员归属校验 → 角色权限校验（防越权）
- mysql2 参数化查询（防 SQL 注入）；短信验证码同手机号 60s 限流（防轰炸）
- 文件上传预签名 URL，限定 MIME 类型与大小；DB 密码 / JWT_SECRET 仅存 CloudRun 环境变量
- 符合《儿童个人信息网络保护规定》：儿童信息收集单独获得监护人同意，最小化收集

### 7.2 AI 协作规范（.agents/）

项目为 AI Agent 协作做了完整的规则与技能体系建设：

- **6 条领域规则**：API 约定、CloudBase 约定、部署约定、前端编码、小程序开发、CI 预览
- **7 个技能**（`.agents/skills/`）：开发、部署、设计、PRD 写作、数据库设计、Web→小程序迁移、CloudBase 平台路由
- 所有任务先匹配路由表再开工，保证开发质量与一致性

### 7.3 关键技术约定

- API 无全局响应包装，直接返回原始数据；列表端点返回 `T[]`
- API 路径必须含 `/api` 前缀（如 `/api/family/:familyId/records/feeding`）
- 全站禁用 emoji，使用 SVG 图标；枚举标签集中定义，禁止组件内散落
- 前端传时间禁用 `toISOString()`（避免 UTC 8 小时偏差），统一 `dayjs().format('YYYY-MM-DDTHH:mm:ss')` 本地时间字符串
