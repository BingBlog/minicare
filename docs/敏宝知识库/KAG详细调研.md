## 一、概览

| 项 | 信息 |
|---|---|
| 全称 | Knowledge Augmented Generation（知识增强生成） |
| 团队 | 蚂蚁集团知识图谱团队 + 浙江大学 |
| 发布 | 2024-10 开源（OpenSPG V0.5 起） |

| 配套 | OpenSPG（语义增强可编程图谱引擎）+ TuGraph-DB（图存储）+ LLM |

**一句话定位**：KAG 是"**知识图谱 + 大模型**"的专业领域知识服务框架，用图谱逻辑约束 LLM 行为，解决通用 RAG 在医疗/政务/法律等领域"不会推理、会幻觉、不严谨"的问题。

## 二、解决什么问题（为什么叫 KAG 不叫 RAG）

| RAG 的缺陷 | KAG 的解法 |
|---|---|
| 向量相似度 ≠ 知识相关性（字面不像但强相关） | 图谱语义相关性召回 |
| 多跳推理差（"湿疹→过敏进程→检测指征"跨文档关联） | 逻辑形式引导的多步推理 |
| 对数值/时间/规则不敏感 | 逻辑计算算子（Math/Deduce） |
| 幻觉难以抑制（加 RAG 后仍有 30-40%） | 图谱结构化知识约束生成 |
| 检索结果不可解释、难溯源 | 知识-文本互索引，推理过程可追溯 |

## 三、三大核心模块

### 3.1 KAG-Builder（离线知识构建）

职责：非结构化文档 → 结构化知识图谱 + 互索引。

```
输入（PDF/TXT/Markdown/表格/JSON）
  → 语义分块（Chunk：articleID#paraCode#idInPara 三级 ID，保证有序可溯源）
  → 双层实体识别（先领域特定实体，再通用 NER）
  → 关系/事件抽取（LLM 或 OneKE）
  → 语义对齐（概念归一、实体消歧、去重）
  → 领域知识注入（Schema 约束 / 概念术语注入 / 文档结构预定义）
  → 写入 TuGraph（图谱）+ 向量库（互索引）
```

> 💡 敏宝对应：输入就是"20 份源文件解析文本"；**Schema 约束** = 我们已有的概念层设计；**领域术语注入** = CMeKG 词表/概念字典。

### 3.2 KAG-Solver（在线推理解题）

职责：自然语言问题 → 逻辑形式（Logical Form）→ 混合推理 → 答案。

三种算子：**规划**（拆解问题）/ **推理**（图谱推理/逻辑计算）/ **检索**（图谱+文本+向量）

集成四种求解过程：
1. **图谱推理**（KG 查询、SPO 子图检索）
2. **逻辑计算**（数值/时间/集合/逻辑判断）
3. **Chunk 检索**（语义文本检索）
4. **LLM 推理**（生成式推理）

多轮反思机制（SolverPipeline）：
```
while 未满足终止条件:
    规划 → 子问题列表
    对每个子问题执行 推理/检索 → 记录到 memory
    判断答案是否充分（Judge）
    不充分 → 补充问题（SupplyQuery）再跑
生成最终答案（Generator）
```

> 💡 敏宝对应：多轮反思恰好支持"过敏宝宝条件推理"——例如"3 月龄+已确诊 CMPA+回避中"叠加条件，图谱+逻辑算子比纯向量更可靠。

### 3.3 KAG-Model（模型能力增强，可选）

- 增强 NLU/NLI/NLG 三项能力（掩码重建 + 多任务 Prompt 联合训练）
- K-LoRA / AKGF 高效微调，小模型接近大模型效果
- OnePass 端到端检索-生成
- 实证：KAG-Llama2 在 C3/WSC/XSum/Lambda/LCSTS/Race 六项任务全面超越 Llama2（如 Race 68.48 vs 55.64）

> 💡 敏宝：可不训练，直接用 DeepSeek/Qwen 等通用模型跑 Builder+Solver；KAG-Model 是进阶选项。

## 四、五大核心创新详解

### 4.1 LLMFriSPG：LLM 友好的知识表示

三层互补结构（这是 KAG 的精髓，与敏宝完美映射）：

| 层 | 含义 | 敏宝对应 |
|---|---|---|
| **KGcs 知识层** | 严格 Schema 约束的高质量知识（专家/人工构建） | 40 个知识条目（人工审核后） |
| **KGfr 信息层** | 自动抽取的实体/事件图（开放信息抽取） | 从 20 份文本自动抽取的实体关系 |
| **RC 文本层** | 原始文档 Chunk（可溯源上下文） | 源文件解析文本的切块 |

- 概念与实例分离、语义归一 → 支持"牛奶过敏/CMPA/CMA"多词一体
- 知识-文本互链 → 每条结论可溯源到原文（**敏宝溯源硬需求直接满足**）

### 4.2 知识-文本互索引
实体/事件 ↔ Chunk 双向索引，支持图谱到文本、文本到图谱双向追溯。检索时图谱缺信息 → 回落文本检索（覆盖更全）。

### 4.3 逻辑符号引导的混合推理
将问题转为可执行逻辑表达式（Retrieval/Sort/Math/Deduce/Output 五类算子），推理链可解释、可审计。

### 4.4 语义推理知识对齐
六大概念语义关系自动归一：同义(synonym)、上下位(isA)、部件(isPartOf)、包含(contains)、实例归属(belongTo)、因果(causes)。提升跨文档多跳推理的连通性。

### 4.5 KAG-Model
见 3.3。

## 六、部署与使用

### 6.1 安装与启动
```bash
git clone https://github.com/OpenSPG/KAG
# 依赖：OpenSPG 引擎 + TuGraph-DB（Docker 起）+ LLM API（DeepSeek/Qwen/Ollama 均可）
# 或使用官方 Docker 编排（包含 OpenSPG + TuGraph + KAG）
```

### 6.2 使用流程
```python
# 1. 定义 Schema（SPG 类型：实体/概念/事件）
# 2. Builder 索引文档
from kag.builder.default_chain import DefaultChain
chain = DefaultChain("medicine", schema="...")
chain.invoke("源文件/解析文本/")

# 3. Solver 问答
from kag.solver.logic.solver_pipeline import SolverPipeline
solver = SolverPipeline(config)
answer = solver.run(question="宝宝喝了奶粉拉血便，是不是牛奶蛋白过敏？")
```

### 6.3 模型要求
- 抽取：GPT-3.5/DeepSeek/Qwen 级别即可（无需微调）
- 推理：DeepSeek-V2 级别效果最佳（论文评测模型）
- 可本地化：Ollama 部署开源模型，数据不出内网

## 七、对敏宝知识库的适配分析

### 7.1 三层结构完美映射现有资产

```
KAG 层              敏宝资产
────────────────────────────────────────
KGcs 知识层    ←  40 个知识条目（概念层设计 → 人工审核）
KGfr 信息层    ←  20 份源文件解析文本自动抽取
RC 文本层      ←  源文件解析文本/（已就绪）
Schema        ←  知识图谱-概念层设计.md（已就绪）
概念字典       ←  家长口语→医学概念映射（已就绪）
医学示例       ←  KAG 自带 examples/medicine 可参照
```

### 7.2 核心优势（相对其他方案）

| 需求 | KAG 的支撑 |
|---|---|
| **溯源到原文** | 互索引机制，天然满足 |
| **条件化推理**（月龄/确诊状态/喂养方式） | 逻辑形式推理 + 图谱属性 |
| **严谨性**（剂量/禁忌/时限不漂移） | Schema 约束 + 逻辑算子 |
| **解释性**（回答展示推理过程） | Logical Form 可审计 |
| **幻觉抑制** | 图谱知识约束生成 |
| **可商用** | Apache-2.0 |

### 7.3 成本与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 构建复杂度较高 | 需理解 OpenSPG Schema 体系 | 用自带 medicine 示例切入，概念层 Schema 已有 |
| 依赖 LLM API | 抽取+推理都调 LLM | DeepSeek 成本低；可本地 Ollama |
| 运维组件多 | OpenSPG+TuGraph+向量库 | Docker 编排；或先 LightRAG 原型再迁移 |
| 社区/文档 | 中文为主，早期阶段 | 蚂蚁官方 yuque 文档 + 开源社区 |

### 7.4 落地建议（敏宝路线）

```
Phase 0  原型验证（1-2 天）：用 KAG medicine 示例 + 1 份 CMPA 文档跑通 Builder→Solver
Phase 1  Schema 落地：按概念层设计定义 SPG Schema（CMPA 子图先行）
Phase 2  全量构建：20 份文档 Builder 索引 + 三元组人工审核
Phase 3  问答接入：Solver + 风险护栏（emergency 条目强制逻辑）
Phase 4  评估：接《召回质量测评方案》50 题回归
```

## 八、结论（v0.2 修正）

**架构层面：KAG 仍是与敏宝需求契合度最高的设计**（医疗生产验证 90%+、三层知识结构匹配、溯源/条件推理/严谨性三大硬需求都有原生机制、Apache-2.0）。

**但项目活跃度层面（2026-08 实测）：KAG/OpenSPG 已冻结 7-13 个月，必须调整选型判断。**

### 修正后的选型建议（三条路线）

| 路线 | 做法 | 适合 | 风险 |
|---|---|---|---|
| **A. 借鉴架构自研（推荐）** | 采用 KAG 的 LLMFriSPG 三层结构 + 互索引 + 逻辑推理**设计思想**，用活跃组件实现（LightRAG 为底座 + 自研 Schema/溯源层） | 长期产品化，敏宝主推 | 需投入开发，但可控可审核 |
| **B. 直接用 KAG（接受冻结）** | 用 KAG 自带 medicine 示例做原型；代码虽停更但**已过蚂蚁生产验证**，冻结状态=文档代码稳定 | 想快速验证"逻辑推理"效果、不依赖社区新功能 | 遇 bug 需自己修（fork 维护）；依赖老版本 LLM 兼容性 |
| **C. 直接用 LightRAG（活跃但弱推理）** | 38.9k star 日更生态，先落地基础问答 | 快速上线、弱逻辑推理需求 | 无 KAG 的逻辑形式推理与 Schema 严谨性 |

### 推荐执行（A+B 组合）
1. **Phase 0（1-2 天）**：用 KAG medicine 示例 + 1 份 CMPA 文档跑通，**重点验证 Solver 逻辑推理效果**（这是 KAG 独特价值）
2. **决策点**：若逻辑推理效果显著且可接受冻结维护 → 走 B；若发现依赖生态/新模型 → 走 A（用 LightRAG + 借鉴 KAG 思想）
3. **无论哪条路**：Schema（概念层）、互索引溯源、审核流程都要自建，这部分工作不浪费

> ⚠️ 决策前务必先跑 Phase 0 原型，因为"架构最契合"和"项目已冻结"两个事实需要实测权衡。
